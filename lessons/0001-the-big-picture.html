Lesson 1: The Big Picture

Goal: Understand what this repo builds, why it exists, and how the major pieces fit together — so that when you open any file, you know roughly where you are.

What does this project actually do?

Imagine you're a data scientist. You need to:

  • Spin up a notebook (like a JupyterLab coding environment) to experiment with data
  • Train a machine learning model
  • Deploy that model so other applications can use it (called model serving)
  • Build and run pipelines — automated sequences of steps that process data

All of these things run on Kubernetes (we'll explain that in a moment). But Kubernetes is complex — it's all YAML files and command-line tools. Most data scientists don't want to deal with that.

This repo builds the web dashboard that gives data scientists a friendly UI to do all of the above. It's the web app layer on top of the Kubernetes infrastructure.

Two names, one product You'll see two names: Open Data Hub (ODH) is the open-source upstream project. Red Hat OpenShift AI (RHOAI) is Red Hat's supported product built from it. Same codebase, different packaging. Think of it like Chromium vs. Chrome.

What is Kubernetes? (The 2-minute version)

You know how when you write a React app locally, you run npm start and it runs on your laptop? In production, apps don't run on someone's laptop — they run on servers.

Kubernetes (often abbreviated K8s) is a system that manages running applications on many servers. It handles:

  • Scheduling — deciding which server runs your app
  • Scaling — running more copies if traffic increases
  • Self-healing — restarting your app if it crashes

Everything in Kubernetes is described as a resource — a JSON/YAML object with a kind, a metadata.name, and a spec. For example, a "Deployment" resource tells Kubernetes "please run 3 copies of my container image."

OpenShift is Red Hat's distribution of Kubernetes — it adds things like a web console, built-in authentication, and developer-friendly features on top of plain Kubernetes. Same core, extra features.

You don't need to be a K8s expert As a dashboard frontend contributor, you mostly interact with K8s data — you fetch resources, display them, and send updates. You don't need to manage clusters. Think of it as: the dashboard is a CRUD app where the database is Kubernetes.

The shape of the repo: a monorepo

This is not a single app in a single folder. It's a monorepo — one Git repository containing many related packages.

Why? Because the dashboard has grown. Instead of one giant frontend, features are split into independently-developed packages that plug into the main shell at runtime. Think of it like a browser with extensions.

odh-dashboard/ ├── frontend/ ← The main React app (the "host") ├── backend/ ← Node.js/Express API server ├── packages/ ← ~25 feature packages (the "plugins") │ ├── model-registry/ Model registration & versioning │ ├── model-serving/ Deploy models for inference │ ├── gen-ai/ Generative AI / chatbot features │ ├── maas/ Model-as-a-Service │ ├── notebooks/ Jupyter notebook management │ ├── cypress/ Shared test framework │ └── ... More feature packages ├── distributions/ ← Different "flavors" of the dashboard ├── dashboard-operator/ ← Go code that deploys the dashboard itself └── docs/ ← Documentation

The analogy: a mall with shops

Think of it this way:

  • The frontend/ folder is the mall building — the shell, navigation, login, shared layout
  • Each packages/* folder is a shop — it has its own UI, its own features, sometimes its own backend (called a BFF — "Backend For Frontend")
  • The shops plug into the mall at runtime using a technology called Module Federation (we'll cover that later)
  • The backend/ is the mall management office — it handles auth, proxies requests to Kubernetes, and provides shared services

Inside frontend/src/ — the structure that matters

The main frontend follows a specific folder convention. Knowing this saves you from wandering:

FolderPurposeRule
src/pages/ One folder per nav item / route Can import from anywhere
src/concepts/ Shared logic for a domain concept (e.g., "projects", "notebooks") Cannot import from pages/
src/components/ Generic reusable components (not tied to a feature) Can only import from utilities/
src/api/ API call functions (fetch data, create resources) Can only import from utilities/
src/utilities/ Generic helpers (string utils, date formatting, etc.) Cannot import from anything else
The import hierarchy Notice the pattern: pages → concepts → components → utilities. Each layer can import from layers below it, but not above. This prevents circular dependencies and keeps the code organized. This is documented in docs/architecture.md.

How data flows: the request path

When a user clicks something in the dashboard, here's what happens:

Browser (React app) │ ▼ Dashboard Backend (Node.js) │ ▼ Kubernetes API Server │ ▼ Actual resources (notebooks, models, pipelines, etc.)

The React app never talks to Kubernetes directly. It always goes through the backend, which:

  1. Checks that you're authenticated (logged in)
  2. Proxies your request to the Kubernetes API with your credentials
  3. Returns the data back to the frontend

This is important because it means the frontend code deals with Kubernetes resource objects as its data. Instead of a typical REST API returning { id: 1, name: "Alice" }, you'll see objects like:

{
  "apiVersion": "v1",
  "kind": "Namespace",
  "metadata": {
    "name": "my-project",
    "labels": { ... }
  },
  "spec": { ... },
  "status": { ... }
}

Every K8s resource has this shape: apiVersion, kind, metadata, spec, status. You'll see TypeScript types like K8sResourceCommon and NotebookKind throughout the codebase — they describe these shapes.

Your first development commands

To run the dashboard locally, you need Node.js 22+ and access to an OpenShift cluster (for the backend to proxy to). The basic flow:

# Install all dependencies (runs across the entire monorepo)
npm install

# Start frontend + backend in dev mode
npm run dev

# Frontend: http://localhost:4010
# Backend:  http://localhost:4000

Other commands you'll use often:

# Run linting across all packages
npm run lint

# Run type checking across all packages
npm run type-check

# Run unit tests
npm run test-unit

# Run unit tests for just the frontend
npm run test:frontend
