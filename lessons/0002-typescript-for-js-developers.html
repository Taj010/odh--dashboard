Lesson 2: TypeScript for JS Developers

Goal: Read and understand the TypeScript you'll encounter in this codebase. You won't need to become a TS expert — just fluent enough to not be blocked when reading or editing files.

The one-sentence version

TypeScript is JavaScript with labels on your data.

You already write JS. TypeScript adds type annotations — little labels that say "this variable is a string" or "this function returns a number." The computer checks those labels before your code runs, catching bugs that would otherwise show up at runtime.

Every .ts and .tsx file in this repo is TypeScript. Every .js file you've written is already valid TypeScript — TS is a superset of JS.

Primary source The TypeScript for JavaScript Programmers page on the official site is the single best thing to read after this lesson. It's short and assumes JS knowledge — exactly your starting point.

1. Type annotations on variables

In JS, you declare a variable and put whatever you want in it. In TS, you can add a type annotation after the name:

JavaScript
const name = "Alice";
let count = 0;
let isAdmin = true;
TypeScript
const name: string = "Alice";
let count: number = 0;
let isAdmin: boolean = true;

Most of the time, you don't even need the annotation — TypeScript is smart enough to figure it out from the value. This is called type inference:

// TS already knows this is a string — no annotation needed
const name = "Alice";

You'll see annotations most often on function parameters (where TS can't guess) and on complex objects.

2. Type annotations on functions

This is where TypeScript shines — and where you'll see it constantly in this codebase.

JavaScript
const truncateString = (str, length) => {
  if (str.length <= length) {
    return str;
  }
  return str.substring(0, length) + '…';
};
TypeScript
const truncateString = (str: string, length: number): string => {
  if (str.length <= length) {
    return str;
  }
  return `${str.substring(0, length)}…`;
};
This is real code The TS version above is from frontend/src/utilities/string.ts in this repo. The pattern (param: Type): ReturnType is something you'll read hundreds of times.

The : void return type means "this function returns nothing":

// from frontend/src/utilities/string.ts
export const downloadString = (filename: string, data: string): void => {
  const element = document.createElement('a');
  // ... creates a download link and clicks it
};

3. Defining object shapes with type

In JS, objects can have any shape. In TS, you define what shape an object should have using type:

type ExternalLinkProps = {
  text: string;
  to: string;
  testId?: string;  // The ? means this property is optional
};

This is from frontend/src/components/ExternalLink.tsx. It says: "An ExternalLinkProps object must have text (string) and to (string), and may optionally have testId (string)."

The ? means optional You'll see ? everywhere. lastActivity?: number means "this property might not exist." Without the ?, the property is required — TypeScript will error if you forget it.

4. Types on React components

This is the pattern you'll see most often. Here's a real component from the codebase — notice it's almost identical to the React you already write, just with types added:

// frontend/src/components/ExternalLink.tsx

type ExternalLinkProps = {
  text: string;
  to: string;
  testId?: string;
};

const ExternalLink: React.FC<ExternalLinkProps> = ({ text, to, testId }) => (
  <Button
    variant="link"
    data-testid={testId}
    isInline
    component="a"
    href={to}
    target="_blank"
    rel="noopener noreferrer"
    icon={<ExternalLinkAltIcon />}
    iconPosition="end"
  >
    {text}
  </Button>
);

Let's break down the new syntax:

SyntaxWhat it means
type ExternalLinkProps = { ... } Define the shape of the component's props
React.FC<ExternalLinkProps> "This is a React Function Component that accepts ExternalLinkProps"
<ExternalLinkProps> This is called a generic — it's like passing a type as an argument (more on this below)

If you already used PropTypes in React, type replaces that — but it's checked at build time, not runtime, so bugs are caught before the browser.

5. The interface keyword

You'll also see interface — it's almost the same as type for defining object shapes:

type
type WarningNotification = {
  title: string;
  message: string;
};
interface
interface WarningNotification {
  title: string;
  message: string;
}

For day-to-day work in this repo: they're interchangeable. Don't worry about the difference yet. The codebase uses type more often.

6. Enums — named constants

An enum is a way to define a set of named values. You'll see them throughout the codebase for status codes, categories, and resource types:

// from frontend/src/concepts/hardwareProfiles/types.ts
export enum HardwareProfileWarningType {
  HARDWARE_PROFILES_MISSING_CPU_MEMORY = 'hardware_profiles_missing_cpu_memory',
  CANNOT_BE_NEGATIVE = 'cannot_be_negative',
  CANNOT_BE_DECIMAL = 'cannot_be_decimal',
  INVALID_UNIT = 'invalid_unit',
  MISSING_VALUE = 'missing_value',
  OUT_OF_RANGE = 'out_of_range',
  OTHER = 'other',
}

Instead of writing 'out_of_range' as a raw string (easy to mistype), you write HardwareProfileWarningType.OUT_OF_RANGE. TypeScript will autocomplete it and catch typos.

Think of enums as a dropdown menu for your code — they restrict a value to a specific set of options.

7. Union types — "this OR that"

The | symbol means "or":

// This value can be a string or a number
let port: string | number;

// This status must be one of these exact strings
type ConnectionTestStatus = 'not-tested' | 'testing' | 'verified' | 'failed';

String unions (like 'verified' | 'failed') act like lightweight enums — the codebase uses both patterns.

8. Generics — types that take arguments

This is the scariest-looking syntax you'll encounter, but the idea is simple. Generics let you write a type or function that works with multiple types:

// Without generics — only works for strings
function firstItem(items: string[]): string {
  return items[0];
}

// With generics — works for ANY type
function firstItem<T>(items: T[]): T {
  return items[0];
}

firstItem<string>(["a", "b"]);  // returns string
firstItem<number>([1, 2, 3]);   // returns number

The <T> is a placeholder — "I don't know the type yet; the caller will fill it in." You saw this already with React.FC<ExternalLinkProps> — React provides the generic FC<P> component, and you fill in P with your props type.

Real example from this repo:

// from frontend/src/types.ts
export type PrometheusQueryResponse<TResultExtraProps extends object = object> = {
  data: {
    result: ({
      value: [number, string];
    } & TResultExtraProps)[];
    resultType: string;
  };
  status: string;
};
Don't panic about complex generics When you encounter something like <TResultExtraProps extends object = object>, read it as: "This type has a customizable part called TResultExtraProps, which defaults to object." You don't need to master this to contribute — just recognize the pattern.

9. The operators you'll see everywhere

Real usage from frontend/src/utilities/string.ts:

// ?. and ?? working together
options?.multiPrefix ?? ''
// Translation: "If options exists AND has multiPrefix, use it. Otherwise, use empty string."

And from frontend/src/concepts/connectionTypes/types.ts:

export const CONNECTION_TEST_ANNOTATIONS = {
  STATUS: 'opendatahub.io/connection-test-status',
  TIMESTAMP: 'opendatahub.io/connection-test-timestamp',
  MESSAGE: 'opendatahub.io/connection-test-message',
} as const;

That as const means the STATUS field's type isn't just string — it's the exact string 'opendatahub.io/connection-test-status'. This helps TS catch cases where you accidentally pass the wrong annotation key.

10. The & intersection — combining types

Where | means "this OR that," & means "this AND that":

type TolerationSettings = {
  enabled: boolean;
  key: string;
};

type NotebookTolerationFormSettings = TolerationSettings & {
  error?: string;
};

// NotebookTolerationFormSettings has: enabled, key, AND error?

This is from frontend/src/types.ts. It says: "A NotebookTolerationFormSettings is everything in TolerationSettings, plus an optional error field." This is how types get composed — building bigger shapes from smaller ones.
