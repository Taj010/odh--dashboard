Lesson 3: PatternFly — The UI Component Library

Goal: Understand what PatternFly is, how to use it in this codebase, and the rules that govern when to use PF components vs writing custom code.

The one-sentence version

PatternFly is a library of pre-built React components (buttons, tables, modals, layouts) made by Red Hat — and this entire dashboard is built from them.

Instead of writing <button className="my-button"> and styling it from scratch, you import <Button> from PatternFly and it comes with:

  • Consistent visual design (colors, spacing, sizing)
  • Accessibility built in (screen readers, keyboard navigation)
  • Dark mode support (via design tokens)
  • Responsive behavior
Primary source The PatternFly v6 documentation site is where you look up components, copy code examples, and read design guidelines. Bookmark it — you'll use it constantly.

1. Why PatternFly specifically?

PatternFly is Red Hat's open-source design system. Since this dashboard is a Red Hat product (RHOAI / OpenShift AI), using PatternFly means:

  • Consistency — every Red Hat product looks and feels the same to users
  • No design debates — spacing, colors, and interaction patterns are already decided
  • Accessibility for free — PF components follow WCAG guidelines out of the box
  • Less CSS to write — the component handles its own styling

This project uses PatternFly v6 (version 6.4.1). All class names, tokens, and component APIs target v6. If you find examples online for v4 or v5, they might not work here.

3. What a PF component looks like in this codebase

Here's a real component from the repo — a delete confirmation modal. Notice how almost every element is a PatternFly component:

// frontend/src/pages/projects/components/DeleteModal.tsx (simplified)

import {
  Alert,
  Button,
  Flex,
  FlexItem,
  Stack,
  StackItem,
  TextInput,
  Modal,
  ModalBody,
  ModalHeader,
  ModalFooter,
} from '@patternfly/react-core';

const DeleteModal: React.FC<DeleteModalProps> = ({ title, onClose, onDelete, deleteName }) => (
  <Modal isOpen onClose={onClose} variant="small">
    <ModalHeader title={title} titleIconVariant="warning" />
    <ModalBody>
      <Stack hasGutter>
        <StackItem>Type the name to confirm:</StackItem>
        <StackItem>
          <TextInput id="confirm" onChange={(e, val) => setValue(val)} />
        </StackItem>
      </Stack>
    </ModalBody>
    <ModalFooter>
      <Button variant="danger" onClick={onDelete}>Delete</Button>
      <Button variant="link" onClick={onClose}>Cancel</Button>
    </ModalFooter>
  </Modal>
);

Count the PatternFly components: Modal, ModalHeader, ModalBody, ModalFooter, Stack, StackItem, TextInput, Button (×2). Zero custom CSS needed.

5. The rules — how to use PatternFly in this project

This is the most important part of this lesson. This project has strict rules about styling to keep the codebase consistent and maintainable.

The priority order (memorize this)

When you need to make something look a certain way, always try these in order:

1PatternFly component props — Always the default. Use the component's built-in props to get the appearance you want. Example: <Button variant="danger"> instead of adding a red CSS class.
2PF layout components — Use Flex, Stack, Grid, Split, Gallery for arranging things. Don't write display: flex yourself.
3PF utility classes — Classes like pf-v6-u-mb-lg (margin-bottom large). Only if props and layout components can't do it.
4SCSS with PF tokens — Custom CSS as a last resort. Must use PF's design token variables (e.g., var(--pf-t--global--spacer--md)), never hardcoded values like 16px or #333.
What you must NEVER do
  • Write style={{ padding: '16px' }} — inline styles are banned
  • Hardcode colors like color: #c9190b — use tokens
  • Write custom display: flex — use the Flex component
  • Write @media queries — PF components handle responsiveness through their own breakpoint props

Design tokens — PF's variable system

"Design tokens" are CSS variables that PatternFly defines. They're the single source of truth for every color, spacing value, and font size. Here's why they matter:

/* ❌ Hardcoded — breaks in dark mode, inconsistent */
.my-thing {
  padding: 16px;
  color: #333;
  border: 1px solid #d0d7de;
}

/* ✅ PF tokens — adapts to dark mode, always consistent */
.my-thing {
  padding: var(--pf-t--global--spacer--md);
  color: var(--pf-t--global--text--color--regular);
  border: 1px solid var(--pf-t--global--border--color--default);
}

The --pf-t-- prefix means "PatternFly token." When the app switches to dark mode, these variables automatically change value. Hardcoded values don't.

Custom class naming

When you do need a custom class (which should be rare), this project uses a BEM-like convention:

6. How to find the right PF component

Your workflow when building UI:

  1. Think about what you need — "I need a dropdown" or "I need a warning banner"
  2. Search patternfly.org — type your need in the search bar
  3. Read the examples — every component page has live, copyable code examples
  4. Check if this project has a wrapper — some PF components have project-specific wrappers (see below)
  5. Use it — import from @patternfly/react-core and use the props from the docs

Project wrappers to know about

7. Upstream vs. local — when to fix PatternFly itself

This is a judgment call you'll need to make. Here's the decision framework:

SituationAction
A PF component does almost what you need but is missing a prop or behavior File an issue upstream at patternfly-react. Add a local workaround with a // TODO: comment linking the issue.
A PF component has a visual bug (wrong spacing, broken alignment) File upstream + local CSS override using PF component variables. Add a // FIXME: comment with the issue link.
You need domain-specific behavior (e.g., "auto-refresh pipeline status") Build locally using PF primitives. This isn't PF's job.
A component works fine but you want it to look slightly different Don't override — PF's visual choices are intentional. Match the design system.
PF v6 removed or changed an API you were using Migrate locally — PF publishes migration guides (codemods). Follow them.
The "TODO" pattern for PF bugs When you work around a PF bug, always leave a comment so the workaround can be removed later: 
// TODO: Remove when PF bug is fixed.
// See https://github.com/patternfly/patternfly-react/issues/XXXX
.pf-v6-c-drawer__body {
  min-height: 0;
}

8. Keeping up with PatternFly

As a contributor to this project, here's what you need to know about staying current:

What the project handles (not your problem day-to-day)

  • Version upgrades — the team bumps PF versions periodically. The package.json pins the version.
  • Major migrations (v5 → v6) — these are coordinated efforts with codemods. You'll see dedicated PRs.
  • Breaking changes — PF publishes release notes. The team reviews them before upgrading.

What you should be aware of

  • Use v6 patterns only — if you find a Stack Overflow answer using pf-v5-* classes, don't copy it. Check the v6 docs for the current API.
  • PF components can change between minor versions — a prop might get deprecated. If you see a TS warning about a deprecated prop, follow the deprecation message to the replacement.
  • Read the component docs before using — don't guess the API. The docs show you exact prop names and valid values.

9. Reading a real component with fresh eyes

Let's look at ExternalLink.tsx again — now that you know PatternFly:

import { Button } from '@patternfly/react-core';
import { ExternalLinkAltIcon } from '@patternfly/react-icons';

const ExternalLink: React.FC<ExternalLinkProps> = ({ text, to }) => (
  <Button
    variant="link"          // ← PF prop: renders as a link-styled button
    isInline               // ← PF prop: no extra padding, sits inline with text
    component="a"          // ← PF prop: renders as an <a> tag, not <button>
    href={to}
    target="_blank"
    rel="noopener noreferrer"
    icon={<ExternalLinkAltIcon />}   // ← PF icon component
    iconPosition="end"     // ← PF prop: icon goes after the text
  >
    {text}
  </Button>
);

Key observations:

  • Zero custom CSS — everything is controlled by PF props
  • variant="link" — instead of styling a button to look like a link, you tell PF what variant you want
  • component="a" — PF lets you swap the underlying HTML element while keeping the same styling
  • The icon is a React component from @patternfly/react-icons, not an <img> or inline SVG

Key takeaways

  • PatternFly is your primary tool — reach for PF components before writing any custom UI
  • Props first, CSS last — the priority order (props → layout components → utility classes → SCSS) is non-negotiable
  • Tokens, not values — if you must write CSS, use var(--pf-t--*) variables
  • Check for wrappers — this project has custom versions of common PF patterns
  • File upstream for bugs — work around locally with a TODO, but get PF to fix it at the source
  • v6 only — ignore older examples that use pf-v5-* class names
