Lesson 5: How a Page Is Structured

Goal: When you open a page folder in this repo, know what each piece does — route, page shell, data hook, and body — so your next edit lands in the right file.

The one-sentence version

A page is not one file: a route registration points to a folder; that folder fetches data, wraps it in ApplicationsPage, and renders PatternFly UI.

Primary source Read docs/extensibility.md (how app.route / nav plugins work). Then open the real files listed below — the code is the other primary source.

1. The stack from URL → screen

  • URL e.g. /settings/environment-setup/connection-types
  • Route plugin app.route entry in frontend/src/plugins/extensions/routes.ts — maps path → which component to lazy-load
  • AppRoutes frontend/src/app/AppRoutes.tsx turns those plugins into React Router <Route>s
  • *Routes.tsx Optional nested routes inside the feature (list / create / edit)
  • *Page.tsx The page: fetch data → ApplicationsPage → body
  • Sidebar Separate! Nav labels come from navigation.ts, not from the page file
Browser URL │ ▼ plugins/extensions/routes.ts ← "this path loads that component" │ ▼ app/AppRoutes.tsx ← builds <Route> list from plugins │ ▼ pages/.../SomethingRoutes.tsx ← nested paths (optional) │ ▼ pages/.../SomethingPage.tsx ← ApplicationsPage + table/form │ ▼ What you see in the browser

Important: this is not a giant hardcoded route list in App.tsx. Routes are extensions — small declarations the app collects at runtime. Full deep-dive later; for now you only need: to find a page, search the path in routes.ts.

2. Walk one real page: Connection types

We'll use Connection types — a readable settings page under frontend/src/pages/connectionTypes/.

1. Find the route frontend/src/plugins/extensions/routes.ts

Search for connection-types. You'll see type: 'app.route', a path, and a component: () => import('...ConnectionTypeRoutes'). That's the bridge from URL → folder.

2. Nested routes frontend/src/pages/connectionTypes/ConnectionTypeRoutes.tsx

List at /, plus create, edit/:name, duplicate/:name. Same pattern many features use.

3. The page itself (~30 lines) frontend/src/pages/connectionTypes/ConnectionTypesPage.tsx

This is the pattern to memorize:

const ConnectionTypesPage: React.FC = () => {
  const [connectionTypes, loaded, loadError, refresh] =
    useWatchConnectionTypes();

  return (
    <ApplicationsPage
      loaded={loaded}
      loadError={loadError}
      empty={loaded && !connectionTypes.length}
      emptyStatePage={<EmptyConnectionTypes />}
      title={...}
      description="..."
    >
      <PageSection isFilled>
        <ConnectionTypesTable ... onUpdate={refresh} />
      </PageSection>
    </ApplicationsPage>
  );
};
PieceJob
useWatchConnectionTypes()Data hook — returns list + loading + error + refresh
ApplicationsPageShared shell — title, description, spinner, error, empty
PageSectionPatternFly layout region for the body
ConnectionTypesTableThe actual UI once data exists
EmptyConnectionTypesWhat to show when the list is empty
4. Shared shell packages/ui-core/src/components/ApplicationsPage.tsx

Almost every dashboard page uses this. You pass loaded / empty / loadError; it decides whether to show a spinner, error empty-state, custom empty page, or your children.

5. Sidebar label (separate file!) frontend/src/plugins/extensions/navigation.ts

Search settings-connection-types. The title and href here are what appear in the left nav — changing the page title in ApplicationsPage does not change the sidebar.

3. Folder anatomy (what lives where)

Inside a typical pages/<feature>/ folder:

File patternPurpose
*Routes.tsxNested React Router routes for the feature
*Page.tsxTop-level screen: hook + ApplicationsPage
*Table.tsx / componentsBody UI pieces
Empty*.tsxEmpty-state UI
*Modal.tsxDialogs for create/delete/edit actions
utils.ts, const.ts, columns.tsHelpers, constants, table column defs
manage/Create/edit sub-pages (when the flow is bigger)
Where does data fetching live? Often in a useWatch* or use* hook under utilities/, concepts/, or a package — not as raw fetch inside the page. The page calls the hook and wires the tuple into ApplicationsPage. You'll meet useFetch / useFetchState in a later lesson; for now: page asks a hook, hook talks to the API.

4. Skill practice — open and map

Do this in your editor (no need for the app to be running):

  1. Open ConnectionTypesPage.tsx — find the hook call and the four props loaded, loadError, empty, emptyStatePage.
  2. Cmd/Ctrl+click ApplicationsPage — skim how it chooses spinner vs children.
  3. In routes.ts, search connection-types — confirm the path matches the URL pattern.
  4. In navigation.ts, search the same — note title vs the page's TitleWithIcon title.
  5. Bonus: open frontend/src/pages/groupSettings/GroupSettings.tsx — even flatter (almost no nested routes). Same ApplicationsPage idea.
Win for this lesson You can point at any *Page.tsx and say: “hook → ApplicationsPage → body,” and you know to look in routes.ts / navigation.ts for URL and sidebar.

Keep the glossary open while you read — new terms from this lesson are there.

Key takeaways

  • URL → routes.ts → page folder — start there when hunting a screen
  • Page pattern: hook → ApplicationsPage → PatternFly body
  • Nav is separate: navigation.ts owns sidebar labels/hrefs
  • Don't put API calls in JSX — call a use* hook
  • Extensions, not a mega App.tsx route table — plugins register routes
