Lesson 6: Frontend Folder Map

Goal: Know where to find things in the frontend source. When you get a task like "fix the model serving table," you should immediately know which folder to open.

The one-sentence version

Pages are in pages/, reusable domain logic is in concepts/, API calls are in api/, and shared components live in components/.

1. The big picture

frontend/src/ ├── app/ ← App shell (routes, nav, providers, feature flags) ├── pages/ ← One folder per top-level page/section ├── concepts/ ← Reusable domain logic (hooks, types, components) ├── api/ ← K8s API call functions ├── components/ ← Shared generic UI components ├── routes/ ← Route path definitions by feature area ├── plugins/ ← Module Federation / extension system ├── utilities/ ← Pure helper functions (no React) ├── services/ ← Service layer ├── redux/ ← Global state management ├── images/ ← SVGs and static images └── __mocks__/ ← Shared test mock data

2. pages/ — where features live

Each subfolder under pages/ corresponds to a top-level section in the dashboard navigation. Examples:

FolderDashboard section
pages/projects/Data Science Projects
pages/modelServing/Model Serving
pages/pipelines/Pipelines
pages/hardwareProfiles/Hardware Profiles (admin)
pages/connectionTypes/Connection Types (admin)
pages/notebookController/Workbench controller
pages/home/Home / landing page

Inside a page folder you'll typically find:

pages/hardwareProfiles/
├── HardwareProfiles.tsx          ← Main page component
├── HardwareProfilesTable.tsx     ← Table component
├── ManageHardwareProfile.tsx     ← Create/edit form page
├── components/                   ← Sub-components specific to this page
├── utils.ts                      ← Helper functions for this page
└── __tests__/                    ← Unit tests for this page
Rule of thumb If a component is only used within one page section, it lives in that page's folder. If it's used across multiple pages, it goes in concepts/ or components/.

3. concepts/ — reusable domain logic

This is the heart of the codebase's reusable logic. Each subfolder represents a domain concept — a type of Kubernetes resource or business entity the dashboard manages.

FolderWhat it manages
concepts/projects/Data Science Projects (K8s Namespaces with labels)
concepts/pipelines/Pipeline definitions, runs, experiments
concepts/modelServing/InferenceServices, model servers
concepts/k8s/Generic K8s resource utilities (Pods, ConfigMaps, etc.)
concepts/areas/Feature flag system (which features are enabled)
concepts/connectionTypes/Connection type definitions
concepts/hardwareProfiles/Hardware profile resources
concepts/trustyai/TrustyAI / model explainability

A typical concept folder looks like:

concepts/pipelines/
├── types.ts                      ← TypeScript types for this domain
├── usePipelines.ts               ← React hooks for fetching data
├── apiHooks.ts                   ← Hooks that call the API layer
├── content/                      ← Sub-components (tables, forms)
├── context/                      ← React Context providers
└── utils.ts                      ← Domain-specific helpers

4. api/ — Kubernetes API calls

Functions that make actual HTTP requests to the backend (which forwards them to Kubernetes). Organized by resource type:

api/
├── k8s/                          ← Direct K8s resource operations
│   ├── projects.ts               ← CRUD for namespaces/projects
│   ├── configMaps.ts             ← ConfigMap operations
│   ├── secrets.ts                ← Secret operations
│   └── ...
├── pipelines/                    ← Pipeline-specific API calls
├── modelServing/                 ← Model serving API calls
└── ...
Don't call fetch() directly This project has API utilities that handle auth headers, error parsing, and typing. Always use the existing patterns in api/ — never write raw fetch() in a page component.

5. components/ — shared UI building blocks

Generic components that aren't tied to any specific domain:

ComponentWhat it is
components/table/Table wrapper with pagination, sorting, filtering
components/DashboardModalFooter.tsxStandard modal footer (submit/cancel buttons)
components/EmptyTableView.tsx"No data" placeholder for tables
components/ResourceNameTooltip.tsxShows K8s name vs display name

6. app/ — the shell

This is where the application boots and routes are defined:

app/
├── App.tsx                       ← Root component
├── AppRoutes.tsx                 ← Route definitions (React Router)
├── NavSidebar.tsx                ← Left navigation menu
├── AppContext.tsx                ← Global app context providers
└── ...

When you need to add a new page to the navigation or register a new route, this is where you go.

7. Finding things — your workflow

When you get a task, use this mental flow:

  1. What page is it on? → Go to pages/{pageName}/
  2. Does it use shared domain logic? → Check concepts/{domain}/
  3. Does it make API calls? → Check api/{domain}/
  4. Is it a generic UI widget? → Check components/
  5. Is it a routing/navigation change? → Check app/
Pro tip: Search by visible text If you can see it in the browser, you can find it in the code. Use Cmd+Shift+F (global search) and search for the exact text string you see in the UI. That's often the fastest way to find a component.

8. Where tests live

Test typeLocation
Unit tests (Jest)__tests__/ folders next to the code they test
Cypress mock testspackages/cypress/cypress/tests/mocked/
Cypress E2E testspackages/cypress/cypress/tests/e2e/

Check your understanding

1. A hook that fetches pipeline data is used by three different pages. Where does it live?

2. You need to fix a table on the Hardware Profiles admin page. Where do you start looking?

3. Why shouldn't you write raw fetch() in a page component?

Key takeaways

  • pages/ = page-specific components (one folder per nav section)
  • concepts/ = reusable domain logic (hooks, types, context)
  • api/ = network calls to the backend/cluster
  • components/ = generic shared UI widgets
  • app/ = routes, navigation, global providers
  • Search by visible text is the fastest way to find any component
