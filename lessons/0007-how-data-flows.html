Lesson 7: How Data Flows

Goal: Trace how data moves from a Kubernetes resource on the cluster all the way to pixels on your screen — and back when the user submits a form.

The one-sentence version

K8s resource → backend proxy → API function → React hook → component renders it.

1. The full picture

┌─────────────────────────────────────────────────────────────┐ │ CLUSTER (Kubernetes API) │ │ Stores: Projects, Notebooks, InferenceServices, Pipelines… │ └────────────────────────────┬────────────────────────────────┘ │ HTTP (REST) ▼ ┌─────────────────────────────────────────────────────────────┐ │ BACKEND (Node.js / Express) │ │ Proxies K8s calls, adds auth token, sometimes aggregates │ └────────────────────────────┬────────────────────────────────┘ │ HTTP (internal) ▼ ┌─────────────────────────────────────────────────────────────┐ │ API LAYER (frontend/src/api/) │ │ Functions like getProjects(), createNotebook() │ │ Typed request/response, error handling │ └────────────────────────────┬────────────────────────────────┘ │ function call ▼ ┌─────────────────────────────────────────────────────────────┐ │ HOOKS (frontend/src/concepts/ or pages/) │ │ useFetchState / custom hooks │ │ Manage loading, error, data states │ └────────────────────────────┬────────────────────────────────┘ │ React state ▼ ┌─────────────────────────────────────────────────────────────┐ │ COMPONENT (pages/) │ │ Renders the data using PatternFly components │ └─────────────────────────────────────────────────────────────┘

2. Layer by layer

Layer 1: Kubernetes resource

Everything in the dashboard represents a K8s resource. A "project" is really a Namespace with specific labels. A "workbench" is a Notebook CR (Custom Resource). Data lives as YAML objects on the cluster.

# A simplified K8s resource (what the cluster stores)
apiVersion: v1
kind: Namespace
metadata:
  name: my-project
  labels:
    opendatahub.io/dashboard: "true"
  annotations:
    openshift.io/display-name: "My Data Science Project"

Layer 2: API function

In frontend/src/api/, typed functions call the backend. They handle the HTTP details so the rest of the app doesn't think about network:

// api/k8s/projects.ts (simplified)
export const getProjects = (): Promise<ProjectKind[]> =>
  k8sListResource<ProjectKind>({
    model: ProjectModel,
    queryOptions: {
      queryParams: { labelSelector: 'opendatahub.io/dashboard=true' },
    },
  });

Key point: this returns a typed Promise. The caller knows exactly what shape the data will be.

Layer 3: React hook

Hooks wrap the API call with state management (loading, error, data). This project uses a pattern called useFetchState:

// concepts/projects/useProjects.ts (simplified)
const useProjects = (): [ProjectKind[], boolean, Error | undefined] => {
  const fetchProjects = React.useCallback(() => getProjects(), []);
  return useFetchState<ProjectKind[]>(fetchProjects, []);
};

useFetchState returns a tuple: [data, isLoading, error]. This is the standard pattern across the entire codebase.

The [data, loaded, error] tuple You'll see this everywhere. It's the project's convention for async data. Every data-fetching hook returns these three values in this order.

Layer 4: Component renders

The page component calls the hook and renders based on the state:

// pages/projects/ProjectsPage.tsx (simplified)
const ProjectsPage: React.FC = () => {
  const [projects, loaded, error] = useProjects();

  if (error) return <ErrorState error={error} />;
  if (!loaded) return <Spinner />;

  return (
    <Table data={projects}>
      {/* table columns and rows */}
    </Table>
  );
};

3. The write path (creating/updating)

When a user fills a form and clicks "Create," the flow reverses:

User clicks "Create" │ ▼ Form component calls API function │ ▼ API function POSTs to backend │ ▼ Backend forwards to K8s API with user's token │ ▼ K8s validates + stores the resource │ ▼ Hook re-fetches → UI updates automatically
// The create call (api layer)
export const createProject = (data: ProjectKind): Promise<ProjectKind> =>
  k8sCreateResource<ProjectKind>({ model: ProjectModel, resource: data });

// In the form component
const handleSubmit = async () => {
  try {
    await createProject(formData);
    navigate('/projects');  // success → redirect
  } catch (e) {
    setError(e);  // show error in the form
  }
};

4. K8s resource shapes (types)

Every K8s resource follows the same basic structure. The TypeScript types enforce this:

// The base shape every K8s resource has
interface K8sResourceCommon {
  apiVersion: string;
  kind: string;
  metadata: {
    name: string;
    namespace?: string;
    labels?: Record<string, string>;
    annotations?: Record<string, string>;
    uid?: string;
    creationTimestamp?: string;
  };
}

// A specific resource adds its own spec/status
interface NotebookKind extends K8sResourceCommon {
  spec: {
    template: { /* pod template */ };
  };
  status?: {
    conditions: Condition[];
  };
}
spec vs status
  • spec = what you want (user's desired state)
  • status = what is (cluster's reported current state)
You write to spec. Kubernetes fills status. The dashboard reads both.

5. Context providers

Some data is needed by many components deep in the tree. Instead of passing it through every component (prop drilling), this project uses React Context:

// A context provides data to all children
<ProjectContext.Provider value={{ project, notebooks, pipelines }}>
  <ProjectDetails />    {/* can access project data */}
  <NotebookList />      {/* can access notebooks */}
</ProjectContext.Provider>

// Any child component:
const { notebooks } = useProjectContext();

Context folders live inside concepts/: e.g., concepts/projects/context/.

6. Refresh patterns

The dashboard uses polling to keep data fresh (K8s doesn't push updates to the frontend directly):

  • Periodic refresh — hooks refetch on an interval (e.g., every 30 seconds)
  • Manual refresh — after a mutation (create/edit/delete), explicitly refetch
  • Navigation refresh — re-fetch when navigating to a page

Key takeaways

  • Data flows down: K8s → backend → API function → hook → component
  • Writes go up: form → API function → backend → K8s → refetch → UI updates
  • [data, loaded, error] — the universal return shape for data hooks
  • spec vs status — you write spec, K8s fills status
  • Context — for data shared across many components without prop drilling
  • Never call fetch() directly — use the API layer
