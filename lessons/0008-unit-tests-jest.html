Lesson 8: Unit Tests with Jest

Goal: Understand how unit tests work in this project, run them, read them, and write a simple one yourself.

The one-sentence version

Jest tests live in __tests__/ folders next to the code they test, and they verify small pieces (functions, hooks, components) in isolation.

1. What is Jest?

Jest is a test runner made by Meta. It:

  • Finds files named *.spec.ts or *.test.ts
  • Runs them in a simulated browser environment (jsdom)
  • Reports pass/fail with helpful error messages

In this project, unit tests verify:

  • Utility functions (pure logic)
  • React hooks (custom hooks)
  • React components (rendering + interactions)

2. Running tests

# Run ALL unit tests (from repo root)
npm run test

# Run tests for a specific file
npx jest frontend/src/pages/hardwareProfiles/__tests__/utils.spec.ts

# Run tests matching a pattern
npx jest --testPathPattern="hardwareProfiles"

# Run in watch mode (re-runs on file save)
npx jest --watch
Turbo caches test results Since this is a monorepo with Turbo, npm run test might skip packages whose code hasn't changed. During active development, run jest directly or use --watch.

4. Anatomy of a test

// __tests__/utils.spec.ts

import { formatDisplayName } from '../utils';

describe('formatDisplayName', () => {
  it('should return the display name when present', () => {
    const result = formatDisplayName({ displayName: 'My Project', name: 'my-project' });
    expect(result).toBe('My Project');
  });

  it('should fall back to the resource name', () => {
    const result = formatDisplayName({ displayName: '', name: 'my-project' });
    expect(result).toBe('my-project');
  });
});

The structure is always:

  1. describe — groups related tests (usually one per function/component)
  2. it (or test) — one specific behavior being verified
  3. expect — the assertion (what should be true)

5. Testing React components

This project uses React Testing Library (RTL) for component tests. The philosophy: test what the user sees, not internal state.

// __tests__/DeleteButton.spec.tsx

import { render, screen, fireEvent } from '@testing-library/react';
import { DeleteButton } from '../DeleteButton';

describe('DeleteButton', () => {
  it('should open the confirmation modal when clicked', () => {
    render(<DeleteButton itemName="my-notebook" onDelete={jest.fn()} />);

    // Find the button by its accessible role + name
    const button = screen.getByRole('button', { name: /delete/i });
    fireEvent.click(button);

    // The modal should appear
    expect(screen.getByText('Type "my-notebook" to confirm')).toBeInTheDocument();
  });
});
Query priority (from RTL docs) Find elements in this order:
  1. getByRole — accessible role (button, heading, textbox)
  2. getByLabelText — form labels
  3. getByText — visible text content
  4. getByTestId — last resort (data-testid attribute)
Avoid testing implementation details like class names or component state.

6. Testing hooks

Custom hooks are tested with renderHook from React Testing Library:

import { renderHook, act } from '@testing-library/react';
import { useCounter } from '../useCounter';

describe('useCounter', () => {
  it('should increment the count', () => {
    const { result } = renderHook(() => useCounter(0));

    act(() => {
      result.current.increment();
    });

    expect(result.current.count).toBe(1);
  });
});

7. Mocking

Tests should run without network calls. You mock external dependencies:

// Mock an API module
jest.mock('~/api/k8s/projects', () => ({
  getProjects: jest.fn().mockResolvedValue([
    { metadata: { name: 'test-project' } },
  ]),
}));

// Mock a hook
jest.mock('~/concepts/projects/useProjects', () => ({
  useProjects: () => [[mockProject], true, undefined],
}));

Shared mock data lives in frontend/src/__mocks__/ — reuse it instead of creating new mocks every test.

8. Common matchers you'll use

MatcherWhat it checks
toBe(value)Strict equality (===)
toEqual(obj)Deep equality (for objects/arrays)
toBeInTheDocument()Element exists in the DOM
toHaveBeenCalledWith(args)Mock function was called with specific args
toHaveLength(n)Array or string has n items/chars
toBeNull()Value is null
toContain(item)Array includes item or string includes substring

9. The rules in this project

  • Every new utility function needs a test
  • Every new hook needs a test
  • Don't reduce code coverage — CI checks coverage and flags drops
  • Reuse shared mocks from __mocks__/
  • Test behavior, not implementation — if you refactor the internals, tests should still pass

Key takeaways

  • __tests__/*.spec.ts(x) beside the code they test
  • describe → it → expect is the basic structure
  • React Testing Library — test what users see (roles, text), not internals
  • Mock external deps — no network calls in unit tests
  • Every new function/hook/component needs a test
