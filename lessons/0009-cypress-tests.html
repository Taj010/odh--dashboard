Lesson 9: Cypress Tests

Goal: Understand the two types of Cypress tests in this project (mock and E2E), how they differ from Jest, and how to run them.

The one-sentence version

Cypress opens a real browser and clicks through the app — "mock" tests use fake API responses, "E2E" tests talk to a real cluster.

1. Cypress vs Jest — when to use which

Jest (unit)Cypress mockCypress E2E
TestsA function, hook, or component in isolationA page or flow with fake dataA full user flow against a live cluster
SpeedVery fast (milliseconds)Fast (seconds)Slow (relies on cluster)
ConfidenceLogic is correctUI renders and flows workEverything works end-to-end
NetworkMocked (jest.mock)Intercepted (cy.intercept)Real cluster responses
Runs inNode.js (jsdom)Real browser (no cluster)Real browser + real cluster

3. Mock tests (your main focus)

Mock tests intercept every API call and return pre-defined responses. The app thinks it's talking to a real cluster, but it's all fake data. This means:

  • No cluster needed to run them
  • Tests are fast and deterministic
  • You control exactly what data appears
// packages/cypress/cypress/tests/mocked/hardwareProfiles/hardwareProfiles.cy.ts

describe('Hardware Profiles', () => {
  beforeEach(() => {
    // Intercept API calls with fake data
    cy.interceptOdh(
      'GET /api/hardware-profiles',
      mockHardwareProfiles,
    );
    // Visit the page
    hardwareProfilesPage.visit();
  });

  it('should display the hardware profiles table', () => {
    hardwareProfilesPage.findTable().should('exist');
    hardwareProfilesPage.findTableRows().should('have.length', 3);
  });

  it('should open the create modal', () => {
    hardwareProfilesPage.findCreateButton().click();
    hardwareProfilesPage.findCreateModal().should('be.visible');
  });
});

4. Page objects — the selector pattern

Instead of writing raw cy.get('[data-testid="..."]') everywhere, this project uses page objects — classes that encapsulate selectors:

// packages/cypress/cypress/pages/hardwareProfiles.ts

class HardwareProfilesPage {
  visit() {
    cy.visit('/hardwareProfiles');
  }

  findTable() {
    return cy.findByTestId('hardware-profiles-table');
  }

  findCreateButton() {
    return cy.findByRole('button', { name: /create/i });
  }

  findTableRows() {
    return this.findTable().find('tbody tr');
  }
}

export const hardwareProfilesPage = new HardwareProfilesPage();
Never write raw selectors in test files Always use page objects. If a data-testid changes, you update it in one place (the page object), not in 20 test files.

5. Key Cypress patterns in this project

cy.interceptOdh

A custom command that intercepts the dashboard's API calls with mock responses:

cy.interceptOdh('GET /api/projects', mockProjects);
cy.interceptOdh('POST /api/projects', { success: true });

Waiting for intercepts (not timers!)

// ✅ Good: wait for the API call to complete
cy.interceptOdh('GET /api/projects', mockProjects).as('getProjects');
cy.wait('@getProjects');

// ❌ Bad: fixed time wait
cy.wait(3000);

Asserting something does NOT exist

// ✅ Correct
cy.findByText('Delete').should('not.exist');

// ❌ Wrong
cy.findByText('Delete').should('have.length', 0);

6. Running Cypress tests

# Open the Cypress GUI (interactive mode)
cd packages/cypress
npx cypress open

# Run mock tests headlessly (CI mode)
npx cypress run --spec "cypress/tests/mocked/**/*.cy.ts"

# Run a specific test file
npx cypress run --spec "cypress/tests/mocked/hardwareProfiles/hardwareProfiles.cy.ts"
Interactive mode is amazing for debugging npx cypress open shows you the actual browser, step by step. You can time-travel through each command and see what the DOM looked like at each point.

7. E2E tests (for context)

E2E tests hit a real cluster. You'll rarely write these as a new contributor — they need specific cluster setup and are slower to develop. But know they exist:

  • They test the real API responses, auth flows, and data persistence
  • They run in CI against a test cluster
  • They catch issues that mocks can't (wrong API shapes, auth problems)

8. When to write which test

ScenarioTest type
New utility function (string formatting, validation)Jest unit test
New React hook (data fetching logic)Jest + renderHook
New page with a table and actionsCypress mock test
Critical user flow (create project end-to-end)Cypress E2E
Bug fix in a form validationJest (for the validation fn) + Cypress mock (for the form)

Key takeaways

  • Mock tests = most common for you; fake data, real browser, no cluster
  • Page objects = always use them for selectors
  • cy.interceptOdh = mock API responses
  • Never cy.wait(number) — wait for intercept aliases instead
  • npx cypress open = interactive debugging (time-travel)
