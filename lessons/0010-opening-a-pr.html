Lesson 10: Opening a PR the ODH Way

Goal: Understand the full workflow from picking up a task to getting your code merged — including the branch conventions, PR template, CI checks, and review process.

The one-sentence version

Branch off main, make small focused commits, fill out the PR template completely, and make sure lint + type-check + tests pass before requesting review.

1. The full workflow

1. Pick up a Jira issue │ 2. Create a branch: RHOAIENG-1234-fix-table-sort │ 3. Make changes (small, focused commits) │ 4. Run locally: lint, type-check, tests │ 5. Push and open PR (fill the template!) │ 6. CI runs automatically │ 7. Address review feedback │ 8. Merge (squash)

2. Branch naming

Branch names should reference the Jira ticket:

# Pattern: {ticket}-{short-description}
git checkout -b RHOAIENG-1234-fix-hardware-profile-sort
git checkout -b RHOAIENG-5678-add-pipeline-delete-modal

If there's no Jira ticket (rare), use a descriptive name:

git checkout -b fix/table-empty-state-spacing

3. Before pushing — run the checks locally

CI will run these anyway, but catching issues locally saves 10+ minutes of waiting:

# Lint (finds code style issues)
npm run lint

# Type checking (finds TypeScript errors)
npm run type-check

# Unit tests
npm run test

# Fix lint issues automatically
npm run lint:fix
Don't push with lint errors CI will fail immediately. Run npm run lint:fix first. If auto-fix can't solve it, read the error message — ESLint tells you exactly what's wrong and often suggests a fix.

4. The PR template

When you open a PR on GitHub, you'll see a template. Fill it out completely. Here's what each section asks:

SectionWhat to write
Jira linkLink to the RHOAIENG ticket
DescriptionWhat you changed and why (not just "fixed the bug")
How to testSteps a reviewer can follow to verify your change works
ScreenshotsBefore/after if it's a UI change (always include these!)
Type of changeCheckbox: bug fix, feature, refactor, etc.
ChecklistConfirm: tests added, no console.log left, lint passes
PRs without a filled template get ignored Reviewers are busy. If they have to guess what your PR does or how to test it, it sits unreviewed. A good description = fast review.

5. What CI checks

When you push, several automated checks run:

CheckWhat it verifiesFails because of
LintCode style and patternsESLint errors, unused imports
Type checkTypeScript compiles cleanlyType errors, missing types
Unit testsJest tests passBroken tests or coverage drop
Cypress mockMock UI tests passBroken selectors, changed behavior
CoverageTest coverage doesn't decreaseNew code without tests

6. Commit messages

This project uses squash merges, so individual commit messages matter less — but keep them clean for your own history:

# Good
git commit -m "fix(hardwareProfiles): sort by name handles empty strings"
git commit -m "feat(pipelines): add delete confirmation modal"

# Bad
git commit -m "fix stuff"
git commit -m "wip"
git commit -m "asdfgh"

7. Responding to review feedback

  • Be responsive — try to address feedback within a day
  • Push new commits (don't force-push during review — it erases the reviewer's context)
  • Reply to every comment — even if just "Done" or "Good point, fixed"
  • Ask questions if feedback is unclear — reviewers appreciate engagement

8. Common PR mistakes (avoid these)

  • Giant PRs — 500+ lines are hard to review. Split into smaller PRs when possible.
  • Leftover console.log — always remove debug logs before pushing
  • Missing tests — new features/fixes need tests. CI checks coverage.
  • No screenshots for UI changes — reviewers can't run your branch easily
  • eslint-disable without explanation — if you must disable a rule, comment why

Key takeaways

  • Branch from main with the Jira ticket in the name
  • Run lint + type-check + tests locally before pushing
  • Fill the PR template completely — description, test steps, screenshots
  • Small PRs > big PRs — easier to review, faster to merge
  • No console.log, no eslint-disable without comments
