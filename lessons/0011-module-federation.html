Lesson 11: Module Federation

Goal: Understand how the monorepo's packages (model-registry, gen-ai, etc.) plug into the main dashboard as independent modules at runtime — and why that matters for your daily work.

The one-sentence version

Module Federation lets each package (packages/*) be built independently and loaded into the main dashboard at runtime, like plugins that snap into a host app.

1. Why not just import everything normally?

In a simple app, all code is bundled together into one giant JavaScript file. But this dashboard is huge and maintained by multiple teams. Module Federation solves:

ProblemHow Module Federation helps
Teams step on each otherEach package is independently developed and built
Build takes foreverOnly rebuild the package that changed
Deploy everything for one changeDeploy a single package without touching others
Hard to add new featuresNew packages plug in without modifying the host

2. The mental model

┌─────────────────────────────────────────────────────┐ │ HOST APPLICATION (frontend/) │ │ The main dashboard shell — nav, routes, providers │ │ │ │ Loads at runtime: │ │ ┌──────────────┐ ┌──────────────┐ ┌───────────┐ │ │ │ model-registry│ │ gen-ai │ │ maas │ │ │ │ (package) │ │ (package) │ │ (package) │ │ │ └──────────────┘ └──────────────┘ └───────────┘ │ │ │ │ Each package exposes components the host renders │ └─────────────────────────────────────────────────────┘

Think of it like a browser with extensions — the browser (host) provides the shell, extensions (packages) add features.

3. Key terms

TermMeaning
HostThe main dashboard app (frontend/) that loads other modules
RemoteA package that exposes components to the host (e.g., packages/model-registry)
Exposed moduleA specific component or page that a remote makes available
Shared dependencyLibraries both host and remote use (React, PatternFly) — loaded once, shared
Webpack configEach package has a webpack config defining what it exposes

4. How a package plugs in

Each package under packages/ has:

packages/model-registry/
├── src/
│   ├── pages/                    ← The pages this package owns
│   ├── concepts/                 ← Domain logic for this package
│   └── index.ts                  ← What's "exposed" to the host
├── webpack.config.ts             ← Module Federation config
├── package.json
└── tsconfig.json

The webpack config tells Module Federation: "I expose these components, and I share these libraries with the host."

5. What this means for your daily work

If you're working in frontend/ (the host):

  • You're working on the shell, shared infrastructure, or pages that aren't in a package
  • Changes here affect everyone
  • You run npm run start:dev:ext from frontend/

If you're working in packages/model-registry/ (a remote):

  • You're working on model-registry-specific pages and logic
  • You can develop in isolation (the package has its own dev server)
  • Your code gets loaded into the host at runtime

Running both together:

# From repo root — starts the host + all packages
npm run dev

# Or start a specific package independently
cd packages/model-registry
npm run start:dev

6. Shared dependencies (why version mismatches matter)

When host and remote both use React, Module Federation shares a single copy. But if versions mismatch:

  • React — must be the same version everywhere (only one React instance allowed)
  • PatternFly — should be the same to avoid style conflicts
  • Other libs — can differ if they don't conflict
Don't add React or PatternFly as a direct dependency in a package These come from the host as shared dependencies. Packages declare them as peerDependencies so npm doesn't install a second copy.

7. Port allocation

Each package runs on its own port during development:

ServicePort
Frontend (host)4010
Backend4000
model-registry4101 (example)
gen-ai4102 (example)
maas4103 (example)

The host knows where to find each remote because the ports are configured in the webpack setup.

8. When you'll encounter Module Federation

  • Adding a new page to a package — you might need to add an exposed route
  • Importing across package boundaries — don't import from other packages directly; use the host's shared layer
  • Build errors about "shared module not found" — usually a missing shared dependency config
  • Creating a new package — requires a full Module Federation setup (see the module-onboarding skill)
You don't need to configure Module Federation day-to-day For most frontend work, you just write components in the right folder and they work. MF configuration is set up once per package.

Key takeaways

  • Module Federation = packages load into the host at runtime (like plugins)
  • Host = frontend/, Remotes = packages/*
  • Shared deps (React, PatternFly) = one copy, used by all
  • Each package has its own port and can be developed independently
  • Day-to-day, you mostly just write components — MF is configured once per package
