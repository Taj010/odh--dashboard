Lesson 13: Area Deep-Dives

Goal: Deep understanding of the specific dashboard areas you'll be working on — what they do, where the code lives, what K8s resources are involved, and how to see them running locally.

The one-sentence version

Each area is a self-contained feature with its own pages, concepts, API calls, and (often) feature flags — this lesson maps all seven areas you'll focus on.

How to use this page This is a reference. Read the area you're about to work on. Each section tells you: what it is, where the code lives, what K8s resources are involved, and how to enable it locally.

1. Agent Ops (Agent Runtimes)

What it is: A feature for deploying and managing AI agents — autonomous LLM-powered tools that can use external tools/APIs. Think: chatbots that can query databases, call APIs, and take actions.

Frontend code
packages/agent-ops/frontend/src/app/pages/agentRuntimes/
K8s resource
AgentRuntime Custom Resource
Feature flags
agentOps, agentOpsDeploy, agentsCatalog (SupportedArea: AGENT_OPS)
BFF
packages/agent-ops/bff/ (Go backend-for-frontend)

What a user does here:

  • Create an agent runtime (choose an LLM, configure tools, set resources)
  • Deploy the agent to the cluster
  • Monitor agent status, logs, and interactions
  • Configure MCP (Model Context Protocol) servers the agent can use

Key concepts:

  • AgentRuntime CR — the K8s resource that defines an agent (model, tools, memory)
  • MCP servers — external tool providers the agent connects to
  • RBAC — users need specific permissions to create/manage agents

How to enable locally:

# Option 1: URL feature flag (precise syntax)
http://localhost:4010?devFeatureFlags=agentOps=true

# Or open the flag launcher:
http://localhost:4010?devFeatureFlags
# Then toggle "agentOps" in the blue banner

# Option 2: Dashboard config on cluster
oc edit odhdashboardconfig -n redhat-ods-applications
# Set in spec.dashboardConfig:
#   agentOps: true

2. RBAC (Role-Based Access Control)

What it is: The system that controls who can do what. In the dashboard, RBAC determines which pages a user sees, which actions are available, and what resources they can access.

Frontend code
frontend/src/concepts/userConfigs/, concepts/areas/
K8s mechanism
SubjectAccessReview (SAR), RoleBindings, ClusterRoles
Feature flag
Always active (core system)
Backend
Backend performs SAR checks on behalf of the user

How RBAC works in this dashboard:

  1. User logs in (via OpenShift OAuth)
  2. Dashboard checks if user is admin (cluster-admin or dashboard-specific role)
  3. Non-admin users see a limited UI (no admin pages, fewer actions)
  4. Before performing actions, the backend checks if the user's token has permission

Key patterns in the code:

// Check if user is admin
const { isAdmin } = useUser();

// Conditionally show admin-only content
{isAdmin && <AdminPanel />}

// RBAC-gated actions
// The backend returns 403 if user lacks permission
// The frontend should hide buttons the user can't use

Common RBAC issues:

  • Don't assume isAdmin means "can do everything" — check specific permissions
  • Hide controls the user can't use — don't show a "Delete" button if they'll get 403
  • Test both paths — admin AND non-admin users

3. MLflow

What it is: An experiment tracking and model registry platform. In RHOAI, MLflow integration lets users track metrics, parameters, and artifacts from their training runs — visible in the dashboard.

Frontend code
packages/mlflow/ (federated module) + frontend/src/concepts/mlflow/ (hooks/selectors)
K8s resource
MLflowServer CR (needs the MLflow operator installed)
Feature flag
SupportedArea: MLFLOW — requires DataScienceStackComponent.MLFLOW
Operator
MLflow Operator (separate install)

What a user does:

  • View experiment runs and their metrics (loss, accuracy, etc.)
  • Compare runs across experiments
  • Register models from successful runs
  • Access the MLflow UI (embedded or linked)

How to see it locally:

# MLflow requires the MLflow operator installed on your cluster
# Check if the CRD exists:
oc get crd mlflowservers.mlflow.org

# If not installed, the dashboard won't show MLflow features
# Ask your team for a cluster with MLflow operator pre-installed

# Or: the dashboard gracefully hides MLflow if CRD is absent

Code pattern:

// The dashboard checks if the MLflow CRD exists on the cluster
// If yes → show MLflow features
// If no → hide them (no error, just absent)
// This is the "CRD discovery" pattern used across the dashboard

4. MCP Registry

What it is: A registry of Model Context Protocol (MCP) servers — tools and data sources that AI agents can use. Think of it as a catalog of "plugins" for AI agents.

Frontend code
packages/mlflow/ (MCP registry handler in BFF + frontend module)
K8s resource
MCP server configurations (ConfigMaps or CRs)
Feature flag
mcpRegistry (SupportedArea: MCP_REGISTRY) — tech preview
Relates to
Agent Ops — agents consume MCP servers

What it manages:

  • List of available MCP servers (tools the agents can use)
  • Server configuration (URL, auth, capabilities)
  • Which agents have access to which MCP servers
  • Health status of registered servers

Key concept — MCP (Model Context Protocol):

MCP is a standard for connecting AI models to external tools. An MCP server might provide:

  • Database queries (agent can look up records)
  • API calls (agent can create tickets, send emails)
  • File access (agent can read/write documents)
  • Web browsing (agent can fetch pages)

Enable locally:

# MCP Registry has its own flag (tech preview)
http://localhost:4010?devFeatureFlags=mcpRegistry=true

# Or use the dev flags banner to toggle "mcpRegistry"
# Note: lives in the mlflow package, not agent-ops

5. Hardware Profiles

What it is: Admin-defined templates that set CPU, memory, and GPU allocations for workbenches and model servers. Instead of users guessing resource amounts, admins create named profiles like "Small (2 CPU, 8Gi RAM)" or "GPU Large (4 NVIDIA A100)".

Frontend code
packages/hardware-profiles/ (source), frontend/src/pages/hardwareProfiles/, concepts/hardwareProfiles/
K8s resource
HardwareProfile Custom Resource
Feature flag
Generally available (no flag needed)
Admin only
Creating/editing profiles is admin-only; users just select them

What an admin does:

  • Create hardware profiles (name, description, resource limits)
  • Set tolerations (which GPU nodes the workbench can schedule on)
  • Enable/disable profiles
  • Set as default for new workbenches

What a user sees:

  • A dropdown when creating a workbench: "Select hardware profile"
  • Profile name + resource summary (e.g., "Medium — 4 CPU, 16Gi RAM")

Code structure:

pages/hardwareProfiles/
├── HardwareProfiles.tsx          ← Admin list page
├── ManageHardwareProfile.tsx     ← Create/edit form
├── HardwareProfilesTable.tsx     ← Table component
└── components/
    ├── NodeResourceSection.tsx   ← CPU/memory inputs
    ├── TolerationSection.tsx     ← GPU toleration config
    └── ...

Enable locally:

# Hardware Profiles should be visible in the admin nav
# Make sure you're logged in as an admin user
# Navigate to: Settings → Hardware profiles
# If the nav item is missing, check the dashboard config:
oc get odhdashboardconfig -o yaml
# Look for: disableHardwareProfiles: false

6. Pipelines

What it is: Kubeflow Pipelines integration — lets users define, run, and monitor automated ML workflows (data preprocessing → training → evaluation → deployment).

Frontend code
frontend/src/pages/pipelines/, concepts/pipelines/
K8s resources
Pipeline, PipelineRun, Task (Tekton/KFP)
Feature flag
Requires Data Science Pipelines Application (DSPA) installed per project
Backend
Talks to the KFP API server (separate from the K8s API)

What a user does:

  • Upload/import pipeline definitions (YAML or from a notebook)
  • Create pipeline runs (one-time or scheduled)
  • View run status, logs, and artifacts
  • Compare runs across experiments
  • Create experiments to group related runs

Key concept — DSPA (Data Science Pipelines Application):

Pipelines aren't available by default in a project. An admin must install a DSPA resource in the namespace first. The dashboard checks for this and shows "Configure pipelines" if it's missing.

How to see pipelines locally:

# Check if DSPA exists in your project
oc get datasciencepipelinesapplications -n your-project

# If not:
# 1. Navigate to your project in the dashboard
# 2. Click "Pipelines" in the project nav
# 3. You'll see "Configure pipeline server" prompt
# 4. Or ask your admin to create a DSPA

# The dashboard shows pipelines differently:
# - No DSPA: "Configure pipeline server" empty state
# - DSPA exists but no pipelines: "Import pipeline" empty state
# - DSPA + pipelines: full pipeline list/table

7. Test Connections

What it is: A feature that verifies data connections work before using them — tests that credentials are valid and the endpoint is reachable.

Frontend code
frontend/src/concepts/connectionTypes/ (test connection logic)
Mechanism
Backend makes a test request using the provided credentials
Feature flag
SupportedArea: CONNECTION_TEST
Related to
Connection Types, Data Connections

What a user does:

  • Fill in connection details (endpoint URL, credentials, bucket name)
  • Click "Test connection" before saving
  • See success/failure feedback
  • Troubleshoot connection issues before they break a pipeline

How it works under the hood:

  1. User enters connection details in the form
  2. Clicks "Test connection"
  3. Frontend sends the details to the backend
  4. Backend attempts to connect (e.g., lists S3 bucket contents)
  5. Returns success or a descriptive error

Enable locally:

# Test connections requires a real endpoint to test against
# For S3: you need a real (or MinIO) S3 endpoint
# The dashboard config may need:
#   disableConnectionTypes: false

# To see the "Test" button:
# 1. Go to a project
# 2. Click "Data connections" or "Add connection"
# 3. Fill in credentials
# 4. Look for "Test connection" button

Key takeaways

  • Each area has a clear code home — either in pages/ + concepts/ or in a packages/ module
  • Feature flags gate new features — use ?devFeatureFlags to toggle them
  • CRD presence gates features — some features only show when an operator is installed (MLflow, Pipelines)
  • Admin vs user views differ — always think about which role sees what
  • Agent Ops + MCP Registry are in the gen-ai package
  • Hardware Profiles + Pipelines are in the main frontend
