Lesson 14: Dashboard Navigation & Setup

Goal: A practical guide to getting every feature area visible in your local dashboard — feature flags, CRDs, operators, and cluster setup for each area.

The one-sentence version

Some features "just work" locally, some need a feature flag toggled, and some need operators installed on the cluster — this lesson tells you which is which.

1. The Feature Flag System

The dashboard has a dev-mode feature flag system. To access it:

# Open the flag launcher (shows all toggles)
http://localhost:4010?devFeatureFlags

# Or enable specific flags directly
http://localhost:4010?devFeatureFlags=agentOps=true
http://localhost:4010?devFeatureFlags=mcpRegistry=true,agentOps=true

This shows a blue banner at the top of the page with toggles for every feature flag. Changes are saved to session storage (odh-feature-flags) and persist until you clear them. They only affect your browser session (not the cluster).

Feature flags vs. dashboard config
  • URL flags (?devFeatureFlags) — local, temporary, for development only
  • OdhDashboardConfig — cluster-wide, persistent, affects all users
In production, feature availability is controlled by the OdhDashboardConfig CR.

How the dashboard config works:

# View the dashboard's configuration
oc get odhdashboardconfig odh-dashboard-config -n redhat-ods-applications -o yaml

# Key section (simplified):
spec:
  dashboardConfig:
    disablePipelines: false            # Pipelines visible (disable* = inverted!)
    disableModelServing: false         # Model Serving visible
    disableHardwareProfiles: false     # Hardware Profiles visible
    agentOps: true                     # Agent Ops visible (newer flags aren't inverted)
    mcpRegistry: false                 # MCP Registry hidden
    # ... many more flags
Watch the naming! Older flags use disable* (inverted: true = hidden). Newer flags like agentOps, mcpRegistry are direct (true = visible). Always check which style the flag uses.

To enable a feature on the cluster:

oc edit odhdashboardconfig odh-dashboard-config -n redhat-ods-applications
# Change disableXXX: true → false
# Save and exit — dashboard reloads config automatically

2. The three levels of feature activation

LevelWhat's neededExamples
Level 1: Just works No extra setup — always visible Projects, Home, Cluster Settings
Level 2: Feature flag Toggle in dashboard config or URL flag Agent Ops, MCP Registry, some experimental features
Level 3: Operator/CRD An operator must be installed on the cluster MLflow (needs MLflow Operator), Pipelines (needs DSPA)

3. Setup guide per area

Hardware Profiles Easy

Difficulty: Just needs admin access.

  1. Log in as a user with admin/cluster-admin role
  2. Navigate to Settings → Hardware profiles in the left nav
  3. If the nav item is missing: oc edit odhdashboardconfig → set disableHardwareProfiles: false

To create test data:

# Apply a sample hardware profile
oc apply -f - <<EOF
apiVersion: dashboard.opendatahub.io/v1alpha1
kind: HardwareProfile
metadata:
  name: small-cpu
  namespace: redhat-ods-applications
spec:
  displayName: "Small CPU"
  description: "2 CPUs, 8Gi RAM — for light workloads"
  enabled: true
  identifiers:
    - identifier: cpu
      displayName: CPU
      defaultCount: 2
      maxCount: 4
      minCount: 1
    - identifier: memory
      displayName: Memory
      defaultCount: 8Gi
      maxCount: 16Gi
      minCount: 4Gi
EOF

Agent Ops / Agent Runtimes Medium

Difficulty: Needs feature flag + agent-ops package running.

  1. Enable the feature flag: 
    # Via URL
http://localhost:4010?devFeatureFlags=agentOps=true

# OR via cluster config
oc edit odhdashboardconfig
# Set: agentOps: true
  2. Start the agent-ops package (if developing in it): 
    cd packages/agent-ops
npm run start:dev
  3. The BFF needs to be running too (Go service): 
    cd packages/agent-ops/bff
go run ./cmd/main.go
  4. Navigate to the Agent Runtimes section in the dashboard

Without the BFF running, the UI will show but API calls will fail.

MCP Registry Medium

Difficulty: Separate flag from Agent Ops; lives in the mlflow package.

  1. Enable the feature flag: 
    http://localhost:4010?devFeatureFlags=mcpRegistry=true
  2. MCP Registry is part of the packages/mlflow/ module (BFF handler)
  3. Navigate to the MCP servers section in the dashboard

RBAC Easy

Difficulty: Always active — you just need to test with different user roles.

  1. Admin view: Log in as a cluster-admin user → see all admin pages
  2. User view: Log in as a regular user → see limited pages 
    # Check your current role
oc auth can-i --list

# Or check if you're admin
oc auth can-i get odhdashboardconfigs -n redhat-ods-applications
  3. To test both roles, you need accounts with different permissions on your cluster

The dashboard determines admin status by:

  • Checking if the user can perform specific actions (SAR check)
  • Checking group membership (configurable in dashboard config)

MLflow Hard

Difficulty: Needs an operator installed on the cluster.

  1. Check if the MLflow CRD exists: 
    oc get crd | grep mlflow
# If nothing shows, the operator isn't installed
  2. If not installed, options:
    • Ask your team for a cluster that has it
    • Install the MLflow operator yourself (OperatorHub)
    • Work with mock data in tests (Cypress mock tests don't need the operator)
  3. Once the CRD exists, the dashboard auto-discovers it and shows MLflow features

Without the operator: The dashboard silently hides MLflow features. No error, they just don't appear.

Pipelines Medium

Difficulty: Needs DSPA installed in the project namespace.

  1. Check if Data Science Pipelines is available: 
    oc get crd datasciencepipelinesapplications.datasciencepipelinesapplications.opendatahub.io
  2. If the CRD exists, create a DSPA in your project: 
    # The dashboard can do this for you via the UI
# OR manually:
oc apply -f - <<EOF
apiVersion: datasciencepipelinesapplications.opendatahub.io/v1alpha1
kind: DataSciencePipelinesApplication
metadata:
  name: dspa
  namespace: your-project
spec:
  apiServer:
    deploy: true
  persistenceAgent:
    deploy: true
  database:
    mariaDB:
      deploy: true
  objectStorage:
    minio:
      deploy: true
EOF
  3. Wait for DSPA pods to become ready: 
    oc get pods -n your-project | grep ds-pipeline
  4. Navigate to your project → Pipelines tab

Different states you'll see:

  • No DSPA CRD → Pipelines section hidden entirely
  • CRD exists, no DSPA in project → "Configure pipeline server" prompt
  • DSPA exists, no pipelines → "Import a pipeline" empty state
  • DSPA + pipelines → Full pipeline list

Test Connections Easy

Difficulty: Just needs a project with connection types configured.

  1. Navigate to a project in the dashboard
  2. Go to Connections or Add data connection
  3. Fill in connection details (S3 endpoint, credentials)
  4. Look for the "Test connection" button

To actually test successfully: You need a real endpoint (MinIO, AWS S3, etc.). Without one, you can still see the UI — the test will just fail with a connection error.

Not seeing something? Check in this order:
  1. Are you logged in as admin? (Settings section is admin-only)
  2. Is the feature flag enabled? (?devFeatureFlags)
  3. Is the CRD installed? (oc get crd | grep SOMETHING)
  4. Is the operator running? (oc get pods)

6. Developing without a cluster (mock-only)

Sometimes you don't have cluster access. You can still work:

  • Cypress mock tests — test entire flows with fake data, no cluster needed
  • Jest unit tests — test logic and components in isolation
  • Storybook (if available) — preview components without the full app
  • Frontend-only with errors — the UI renders, API calls fail, but you can still develop UI components
Pro tip: Start with mock tests If you're adding a new table or form and don't have cluster access yet, write the Cypress mock test first. It forces you to think about the UI flow and provides instant feedback — and your PR already has test coverage when you're done.

Key takeaways

  • ?devFeatureFlags — your main tool for toggling features locally
  • Three levels: just works → needs flag → needs operator
  • OdhDashboardConfig controls feature visibility cluster-wide
  • CRD discovery — the dashboard auto-hides features whose CRDs aren't installed
  • Admin nav is hidden for regular users — test with both roles
  • You can develop without a cluster using mock tests and the frontend-only mode
