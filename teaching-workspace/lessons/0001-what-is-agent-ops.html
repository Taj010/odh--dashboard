Goal: Understand what the agent-ops feature does and why it exists.

Primary Source: packages/agent-ops in the odh-dashboard repository.

The Big Picture

Imagine you're running a restaurant. You have chefs (AI agents) that can cook different dishes (perform tasks). Agent Ops is like a kitchen management dashboard — it lets you:

  • See all the chefs working in your kitchen
  • Start a new chef's shift (deploy an agent)
  • Send a chef home (stop an agent)
  • See what each chef is doing (get agent details)
  • Fire a chef (delete an agent)

In technical terms: Agent Ops is a web UI that lets users deploy, monitor, and manage AI agents running in a Kubernetes cluster.

What is an "Agent"?

An AI Agent is a program that can:

  1. Receive instructions (usually natural language)
  2. Think about what to do
  3. Take actions (call APIs, search, generate code)
  4. Report back results

Examples of agents:

  • A support agent that reads tickets and drafts responses
  • A code assistant that helps developers write code
  • A data analyst that queries databases and creates reports

These agents run as containers in Kubernetes — they're software that runs on servers in the cloud.

What is an "AgentRuntime"?

An AgentRuntime is the running instance of an agent. Think of it like:

  • Agent = The recipe (the code/image)
  • AgentRuntime = A chef actually cooking from that recipe (the running container)

When you "deploy" an agent, you create an AgentRuntime. The runtime has:

AgentRuntime ├── name: "support-agent" ← unique name ├── namespace: "my-project" ← Kubernetes namespace ├── status: "running" ← is it working? ├── containerImage: "quay.io/..." ← what code it runs ├── endpoints: ← how to talk to it │ └── http://support-agent:8080 └── framework: "langgraph" ← what AI framework

The Architecture (How It All Connects)

Agent Ops has three layers. Memorize this — it's the foundation of everything.

┌─────────────────┐ │ FRONTEND │ ← React UI (what you see in browser) │ (Browser) │ └────────┬────────┘ │ HTTP calls ▼ ┌─────────────────┐ │ BFF │ ← Go server (Backend-for-Frontend) │ (Go Server) │ Handles auth, business logic └────────┬────────┘ │ Kubernetes API calls ▼ ┌─────────────────┐ │ KUBERNETES │ ← The cluster where agents run │ Cluster │ Has "Sandbox" Custom Resources └─────────────────┘

Layer 1: Frontend (React)

The web interface users interact with. Built with:

  • React — JavaScript framework for building UIs
  • TypeScript — JavaScript with types (catches bugs early)
  • PatternFly — Red Hat's component library (buttons, tables, forms)

Location: packages/agent-ops/frontend/

Layer 2: BFF (Go)

BFF stands for "Backend-for-Frontend". It's a server that:

  • Receives requests from the frontend
  • Authenticates users (are they allowed?)
  • Talks to Kubernetes on behalf of users
  • Returns data in a format the frontend expects

Location: packages/agent-ops/bff/

Why have a BFF? The browser can't talk directly to Kubernetes. The BFF acts as a secure intermediary that handles auth and translates between the UI and the cluster.

Layer 3: Kubernetes

The cluster where agents actually run. Key concept:

  • Sandbox CR — A "Custom Resource" that defines an agent deployment
  • When you create a Sandbox, Kubernetes automatically creates the Pod (container) and Service (network endpoint)

The Data Flow (Trace a Request)

Let's trace what happens when a user clicks "View Agents":

1. User clicks "Agent Deployments" in the nav │ ▼ 2. Frontend calls: GET /api/v1/agents/runtimes │ ▼ 3. BFF receives request, checks user's auth token │ ▼ 4. BFF calls Kubernetes API: "List all Sandbox CRs" │ ▼ 5. Kubernetes returns list of Sandboxes │ ▼ 6. BFF transforms data into AgentRuntime objects │ ▼ 7. BFF returns JSON to frontend │ ▼ 8. Frontend renders a table of agents

The Contract (OpenAPI)

How do the frontend and BFF agree on what data looks like? They use a contract.

The contract is written in OpenAPI (a YAML file that describes the API). It defines:

  • What endpoints exist (/api/v1/agents/runtimes)
  • What parameters they accept (namespace, limit)
  • What response they return (an AgentRuntimesList)

Location: packages/agent-ops/api/openapi/agent-ops.yaml

Contract-First Development: In this project, you write the OpenAPI spec FIRST, then implement code that matches it. This prevents frontend/backend mismatch bugs.

Key API Operations

What you want to do HTTP Method Endpoint
List all agents GET /api/v1/agents/runtimes
Get one agent's details GET /api/v1/agents/runtimes/{ns}/{name}
Deploy a new agent POST /api/v1/agents/deploy
Stop an agent POST /api/v1/agents/runtimes/{ns}/{name}/stop
Start an agent POST /api/v1/agents/runtimes/{ns}/{name}/start
Restart an agent POST /api/v1/agents/runtimes/{ns}/{name}/restart
Delete an agent DELETE /api/v1/agents/runtimes/{ns}/{name}

Quiz: Check Your Understanding

1. What does BFF stand for?

  • Best Feature Framework
  • Backend-for-Frontend
  • Browser Frontend Fetch
  • Binary File Format

2. What is the relationship between an Agent and an AgentRuntime?

  • They are the same thing
  • Agent is the runtime status
  • Agent is the code; AgentRuntime is the running instance
  • AgentRuntime is the code; Agent is running

3. Why can't the frontend talk directly to Kubernetes?

  • Kubernetes doesn't support HTTP
  • Security: the browser needs a server to handle auth
  • The frontend is written in TypeScript
  • Kubernetes only speaks Go
