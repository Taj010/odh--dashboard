Goal: Understand every field in the module-federation block, how the proxy chain works, why ports matter, and how validate:ports catches mistakes before they reach production.

Why This File Matters

In a normal React project, package.json just lists your dependencies. In this monorepo, it also holds the module-federation config — a custom block that tells the host app:

  • How to find your module (name, entry point)
  • How to route API calls from browser to your BFF (proxy rules)
  • Which ports to use in dev vs production
  • Whether to add auth headers to proxied requests

Think of it as the contract between your module and the host. Get it wrong and nothing connects.

A Real Example: agent-ops

Here is the actual module-federation block from packages/agent-ops/package.json:

"module-federation": {
  "name": "agentOps",
  "remoteEntry": "/remoteEntry.js",
  "authorize": true,
  "tls": false,
  "proxy": [
    {
      "path": "/agent-ops/api",
      "pathRewrite": "/api"
    },
    {
      "path": "/agent-ops/healthcheck",
      "pathRewrite": "/healthcheck"
    }
  ],
  "local": {
    "host": "localhost",
    "port": 9111
  },
  "service": {
    "name": "odh-dashboard",
    "port": 8843
  }
}

Let's break every field down.

Field-by-Field Breakdown

"name": "agentOps"

What: The unique identifier for this module in the Module Federation system.

Analogy: Like a username — the host uses this name to say "load the agentOps remote." Must be unique across all modules. Must be camelCase (no hyphens).

For OpenShell: Would be "openshell"

"remoteEntry": "/remoteEntry.js"

What: The filename webpack/rspack generates that contains the "table of contents" for your module.

Analogy: Like an index page at a library. The host fetches this file first, and it tells the host which components are available and how to load them.

Rule: Always /remoteEntry.js — don't change it.

"authorize": true

What: Tells the host proxy to add the user's auth token to every API request it forwards to your BFF.

Analogy: Imagine a mail room. When you send a letter through the mail room, authorize: true means the mail room stamps your ID badge number on the envelope before forwarding it. The BFF needs that stamp to know who is making the request.

Without it: Your BFF gets requests with no identity — it has to reject them (401).

"tls": false

What: Whether the host-to-module connection uses HTTPS (encrypted) or HTTP (plain).

Analogy: Like choosing between a sealed envelope (TLS true) and a postcard (TLS false). In dev, postcards are fine. In production on the cluster, internal traffic stays within the network, but production configs may flip this to true.

"proxy": [...]

What: The most important part. This is the URL rewrite rule that connects browser requests to your BFF.

We'll explain this in detail below.

"local": { "host": "localhost", "port": 9111 }

What: Where your module's dev server runs on your machine.

Analogy: Like an apartment number. The host dev server runs on port 3000; agent-ops runs on 9111; mlflow on 9110; model-registry on 9100. Each module needs its own "apartment" so they don't crash into each other.

"service": { "name": "odh-dashboard", "port": 8843 }

What: In production (on the cluster), which Kubernetes Service and port serves this module.

Analogy: local is your dev-machine address. service is your production-cluster address. Different locations, same concept.

The Proxy — Explained Simply

What is a proxy? A proxy is a middleman. It receives a request, changes something about it, and forwards it somewhere else. Think of a translator who receives a letter in English, translates it to French, and hands it to the French speaker.

Here's the problem the proxy solves:

The browser can only talk to ONE server: the host (port 3000). But your BFF runs on a DIFFERENT server (port 9111 in dev, port 8843 in prod). Without proxy: Browser --GET /agent-ops/api/v1/agents--> Host (:3000) ---> 404 Not Found! (Host doesn't have that API. It's a React server, not a Go BFF.) With proxy: Browser --GET /agent-ops/api/v1/agents--> Host (:3000) Host sees "/agent-ops/api" matches a proxy rule Host rewrites path: "/agent-ops/api/v1/agents" --> "/api/v1/agents" Host forwards to BFF (:9111 or :8843) BFF --responds with JSON--> Host --forwards to--> Browser

The two-part rewrite

"proxy": [
  {
    "path": "/agent-ops/api",     // MATCH: "if the URL starts with this..."
    "pathRewrite": "/api"          // REPLACE: "...change that prefix to this"
  }
]
Browser sendsHost rewrites toBFF receives
GET /agent-ops/api/v1/agents GET /api/v1/agents /api/v1/agents
GET /agent-ops/api/v1/agents/ns1/bot GET /api/v1/agents/ns1/bot /api/v1/agents/ns1/bot
GET /agent-ops/healthcheck GET /healthcheck /healthcheck

Why strip the prefix?

The BFF doesn't know it's running "inside" the dashboard. It just serves /api/v1/... and /healthcheck. The /agent-ops/ prefix is the host's way of routing — like an apartment building where unit 301 gets mail addressed to "301-Smith", but inside the apartment, it's just "Smith".

OpenShell's proxy would be:

"proxy": [
  {
    "path": "/_bff/openshell/api",
    "pathRewrite": "/api"
  }
]

Note: the spike recommends /_bff/openshell/api (with the _bff prefix), matching mlflow's pattern. The _bff prefix is a convention meaning "this path goes to a BFF sidecar, not to the main host backend."

Port Allocation

Every module needs unique ports — if two modules try to run on the same port, one of them crashes. Here's the current map:

Production ports are separate numbers (8043, 8843, etc.) used inside the Kubernetes cluster. You'll see them in the service.port field and in manifest YAML files.

Why not just pick any number?

  • Dev: You might run multiple modules at once. If agent-ops and openshell both use 9111, one fails to start.
  • Production: Kubernetes Services and NetworkPolicies reference these ports. A conflict means traffic goes to the wrong module.

validate:ports — The Safety Net

The repo has a script that automatically checks for port conflicts. It runs:

  • In the pre-commit hook (every time you commit)
  • In CI (GitHub Actions test workflow)
# What it does (you don't need to run this manually usually):
npm run validate:ports

The script reads every workspace package's module-federation block and:

  1. Collects all local.port values from every package.json
  2. Collects all service.port values from the federation configmap YAML files
  3. Checks for duplicates — if two modules share a port, the script fails with a clear error

Example output when everything is OK:

Local Dev Ports (package.json)
────────────────────────────────────────
  ✓  port 9100  →  modelRegistry
  ✓  port 9110  →  mlflow
  ✓  port 9111  →  agentOps
────────────────────────────────────────

✓ All module federation ports are unique.

Example output when there's a conflict:

  ✗ CONFLICT  port 9111  →  agentOps
  ✗ CONFLICT  port 9111  →  openshell     <-- oops!

✗ Local dev port conflicts detected:

Takeaway: When you scaffold packages/openshell/package.json, use port 9113 for local.port and 8943 for service.port. These were chosen by the spike to avoid conflicts.

The Full Picture: How It All Connects

package.json "module-federation" block │ ├── "name" + "remoteEntry" │ → tells webpack how to bundle │ → host loads remoteEntry.js to discover extensions │ ├── "proxy" │ → tells host dev server to forward API calls │ → in prod: configmap tells the Fastify proxy the same thing │ ├── "local" │ → rspack dev server listens on this port │ → host connects here during local development │ ├── "service" │ → Kubernetes Service + Deployment use this port │ → host connects here in production │ └── "authorize" → host adds auth headers before forwarding → BFF reads those headers to identify the user

What You'll Write for 89723

When you scaffold packages/openshell/package.json for story 89723, here's the block you'll add:

"module-federation": {
  "name": "openshell",
  "remoteEntry": "/remoteEntry.js",
  "authorize": true,
  "tls": false,
  "proxy": [
    {
      "path": "/_bff/openshell/api",
      "pathRewrite": "/api"
    }
  ],
  "local": {
    "host": "localhost",
    "port": 9113
  },
  "service": {
    "name": "odh-dashboard",
    "port": 8943
  }
}

Then run npm run validate:ports to confirm no conflicts. The pre-commit hook will also check automatically.

Quiz

1. What does the proxy's pathRewrite do?

  • Changes the HTTP method from GET to POST
  • Replaces the matched path prefix before forwarding to the BFF
  • Rewrites the response JSON before sending to the browser
  • Redirects the browser to a different URL

2. If "authorize": true, what does the host proxy add to forwarded requests?

  • A CSRF token in a cookie
  • The host's admin password
  • The logged-in user's auth token as a header
  • The Kubernetes cluster certificate

3. Why does each module need a unique local.port?

  • Multiple modules can run simultaneously in dev; same port = crash
  • Kubernetes requires unique port numbers per namespace
  • The browser can only connect to one port at a time
  • npm refuses to install packages with duplicate ports

4. When does validate:ports run automatically?

  • When you run npm install
  • When you start the dev server
  • When you open the browser
  • In the pre-commit hook and in CI

5. The browser sends GET /_bff/openshell/api/v1/workspaces. After proxy rewrite, what URL does the BFF receive?

  • /_bff/openshell/api/v1/workspaces (unchanged)
  • /api/v1/workspaces
  • /v1/workspaces
  • /openshell/api/v1/workspaces
