Part 1: What Even Is a "Spike"?

A spike is a research task. No production code is written. Instead, an engineer (Dan Reed in this case) tries things out to answer questions like:

  • Can we actually import OpenShell's code into our dashboard?
  • What breaks when we try?
  • What's the best approach for production?

The spike produced two documents:

DocumentWhat it is
SPIKE.md The raw findings — "here's what I tried, here's what happened"
FEDERATION-STRATEGY.md The decisions — "based on the findings, here's what we'll do"
Analogy: Imagine you're renovating a house and you need to decide how to connect new plumbing to the existing system. You'd hire a plumber to investigate (the spike): they check pipe sizes, water pressure, where things connect. Then they write a report saying "here's how we should do it" (the strategy). You then do the actual work following their plan.

Part 2: The Big Picture Problem

OpenShell is a separate, standalone application. It has its own:

  • React frontend (its own SPA — Single Page Application)
  • Go backend (its own BFF)
  • Gateway server (the brain that manages workspaces/sandboxes)

Our job is to embed parts of it inside the RHOAI dashboard so users don't have to open a separate website. They should see OpenShell workspaces as a tab in the existing Agent Hub page.

The spike investigated: what's the best way to do that?

BEFORE (standalone): User opens openshell.example.com → OpenShell React SPA → OpenShell Go BFF → OpenShell Gateway (gRPC) AFTER (embedded in dashboard): User opens RHOAI Dashboard > Agents > Workspaces tab → Dashboard host loads OpenShell pages via Module Federation → API calls go through host proxy → OpenShell BFF → OpenShell BFF → Gateway (gRPC)

Part 3: The Four Big Questions (and Their Answers)

The strategy document says there are four independent decisions. Let's translate each one.

Question A: How does OpenShell code get into our project?

Analogy: You want to use a friend's recipe in your restaurant. Do you:
(A1) Buy their cookbook (npm package)?
(A2) Photocopy their handwritten notes (git/file copy)?
(A3) Steal their whole recipe binder and keep it in your kitchen (git subtree/fork)?
(A4) Have them cook in their kitchen and deliver the finished dish (upstream builds the module)?
LOCKED: A1 (npm package), with A2 (file copy) as interim

Decision: OpenShell publishes its UI as an npm package (like any library you npm install). Our package imports from it.

Why: Clean separation. Upstream stays independent. We get versioned releases. When they fix a bug, we just update the version.

Interim: The npm package isn't published yet (upstream PR #11). Until then, the spike used a file: reference to a local build. Think of it as "borrowing the recipe book while the cookbook is at the printer."

Question B: Who builds the Module Federation remote?

Analogy: Your friend's recipe is great, but your restaurant has specific plating standards, garnishes, and table sizes. Do you:
(B1) Buy their ingredients and plate the dish yourself?
(B2) Ask them to plate it in your style too?
(B3) Just put a window between your restaurant and theirs and point at their plates (iframe)?
LOCKED: B1 (ODH adapter builds the MF remote)

Decision: We build the remoteEntry.js in packages/openshell/. We import upstream pages and wrap them in our providers, our routing, our feature flags.

Why: Upstream doesn't need to know about our module federation setup, our PatternFly version, or our auth system. They just provide a library. We do the integration.

REJECTED: B3 (iframe)

What's an iframe? A box inside a webpage that shows another whole webpage. Like a picture-in-picture TV.

Why rejected: Iframes don't share auth, styling, or navigation with the parent app. You'd get double scrollbars, the OpenShell pages wouldn't match the dashboard theme, and you'd have to solve auth twice. Fine for a demo, terrible for a product.

Question C: How do we run the OpenShell BFF?

Analogy: The recipe needs a special sauce that only the original chef knows how to make. Do you:
(C1) Hire them to make the sauce and ship it in jars (use their BFF binary)?
(C2) Get the sauce recipe and make it yourself (copy their BFF code)?
(C3) Write your own version of the sauce from scratch (reimplement in ODH)?
LOCKED: C1 (ship upstream BFF as a container image)

Decision: We don't rewrite the Go BFF. We take the exact upstream binary, put it in a container image, and deploy it as a sidecar pod.

Why:

  • The BFF already talks to the gateway via gRPC — reimplementing that would be a lot of duplicated work
  • Auth headers already match what our dashboard sends (x-forwarded-access-token)
  • The healthcheck and readiness endpoints already exist
  • When upstream fixes a bug, we just update the image version

What this means for you: There's no Go code to write in packages/openshell/bff/ for production. The BFF is upstream's container. You only write frontend code + the proxy config.

Question D: What's shared vs. separate at runtime?

When two apps share the same webpage, they need to agree on which libraries to share. The spike found compatibility issues:

LibraryOpenShell usesDashboard usesShare?Risk
React 18.3 18.3 Yes (singleton) Low
PatternFly 6.2 6.4 Yes (singleton) Low (compatible)
React Router v6 v7 No High major mismatch
TanStack Query v5 v4 No High major mismatch
What "singleton" means: Only one copy of the library loads. If both the host and the module try to load their own React, you'd get errors like "hooks can only be called inside a function component" because React doesn't work when two copies exist. A singleton means "use the host's copy, don't load your own."
Why React Router and TanStack Query can't be shared: Imagine you speak English v6 and your coworker speaks English v7 where some words mean completely different things. You'd miscommunicate constantly. Major version bumps (v4→v5, v6→v7) change how functions work. Loading both versions at once would crash. Solution: the module keeps its own copy of these libraries, isolated from the host.

Part 4: The Proxy Chain — How API Calls Actually Travel

This is the part you said confused you most. Let's build it from scratch.

The Problem

Your browser can only talk to one server — the dashboard host. But the OpenShell BFF is a separate server running on a different port (or a different pod in production). How do API calls get from the browser to the BFF?

Step by Step

1
Your code sets the API prefix

In OpenShellWrapper.tsx, you call setApiBasePath('/_bff/openshell'). This tells upstream components: "when you need to fetch data, start all URLs with /_bff/openshell."

2
Upstream component makes an API call

The WorkspaceListPage component runs something like fetch('/_bff/openshell/api/v1/workspaces'). It doesn't know or care about proxies — it just fetches a URL.

3
Browser sends the request to the host server

Since the page was loaded from the dashboard host (e.g., localhost:3000), the browser sends the request there. GET http://localhost:3000/_bff/openshell/api/v1/workspaces

4
Host proxy intercepts and rewrites

The host looks at the URL and finds a matching proxy rule from your package.json:

"path": "/_bff/openshell/api"  →  "pathRewrite": "/api"

So /_bff/openshell/api/v1/workspaces becomes /api/v1/workspaces

It also adds the user's auth token header (authorize: true).

5
Host forwards to the BFF

In dev: sends to localhost:9113 (or wherever the BFF runs).
In production: sends to the Kubernetes Service on port 8943.

6
BFF processes the request

The OpenShell BFF receives GET /api/v1/workspaces with an auth token. It forwards the request to the OpenShell gateway via gRPC. The gateway returns workspace data.

7
Response flows back

Gateway → BFF → host proxy → browser → React Query caches it → component renders a table.

Part 5: Mocks and the On-Ramp to Real Data

This is your other big question: "If I use mock data, how does that connect to a real BFF later?"

The key insight: your code doesn't change

This is the beautiful part of the proxy design. Your React components always call the same URL:

fetch('/_bff/openshell/api/v1/workspaces')

What answers that request changes depending on the environment:

EnvironmentWhat answers the requestWhat you change
Dev with mocks rspack dev middleware returns hardcoded JSON Nothing in your components
Dev with real BFF Upstream Go BFF running locally on :8943 Remove/disable mock middleware; proxy forwards to BFF
Production cluster BFF container in Kubernetes, fronted by host proxy Nothing — configmap handles routing
Analogy: Imagine you're testing a doorbell. You wire it up to a button and speaker. For testing, you have a friend stand outside and push the button (mock). Later, you install the doorbell on the actual front door (real BFF). The doorbell itself didn't change — what changed is who's pushing the button and from where.

The three stages of your development

Stage 1: Mock everything (where you start — story 89723)

  • rspack dev middleware intercepts /_bff/openshell/api/*
  • Returns static JSON that matches the expected API shape
  • No Go BFF, no gateway, no cluster needed
  • You can build and test the entire UI this way

What you're validating: "Do my pages render? Do the routes work? Does the table show data? Does clicking a row navigate to the detail page?"

Stage 2: Connect to upstream BFF locally (story 89726 / auth-bridge)

  • Run the upstream Go BFF binary on your machine: PORT=8943 AUTH_DISABLED=true ./openshell-bff
  • Your proxy in package.json already knows to forward to port 8943 (service.port)
  • Disable or remove the mock middleware
  • BFF still needs a gateway — without one, /readyz returns 503 (not ready), but /healthz returns 200 (alive)

What you're validating: "Does the proxy chain work end-to-end? Do auth headers get forwarded? Does the BFF respond with the expected shape?"

Stage 3: Full cluster with gateway (when RHAISTRAT-1752 lands)

  • BFF runs in a Kubernetes pod alongside the dashboard
  • Gateway is deployed in the cluster
  • Real workspace data flows from gateway → BFF → proxy → browser
  • Auth is fully wired (double-auth via Keycloak)

What you're validating: "Does everything work for real users on a real cluster?"

The point: At every stage, your React components and your package.json proxy config stay the same. What changes is only the other end of the proxy — mock, local BFF, or production BFF. That's the whole design goal. You write your code once and it works across all three stages.

Part 6: Key Spike Findings (the Important Bits)

The spike covers a lot. Here's what matters for your work:

81066 findings (UI consume — your work)

What upstream publishes

Running npm run build:lib in the upstream repo creates five export groups:

  • ./pages — SandboxListPage, SandboxDetailPage (the actual page components you import)
  • ./components — AlertProvider and other shared UI bits
  • ./api — API hooks and utility functions
  • ./types — TypeScript type definitions
  • ./slots — Extension points for cross-module triggers (future)

What the host wrapper must supply

This is the "callback inventory" from the spike. Every item is something upstream pages expect someone to provide:

WhatHow you provide it

This list is basically Lesson 5's provider table — it came directly from the spike.

Known blockers

  • Terminal WebSocket: The terminal tab builds WebSocket URLs with a hardcoded /api/v1 path instead of using apiBasePath. Through the proxy, this breaks. Feature-gate terminal until upstream fixes it.
  • AlertContext coupling: Upstream's alert system still lives under an app/ internal path. Works because they re-export it, but it's messy. Not a blocker, just ugly.
  • LoginPage: Upstream has a standalone login page. Never use it in the dashboard — the dashboard has its own auth. Exclude from routes.

81067 findings (BFF + gateway — Derek's / infra work)

The BFF just works

Dan built the upstream BFF binary and tested it. Key findings:

  • /api/v1/healthz returns 200 OK (liveness — "am I alive?")
  • /api/v1/readyz returns 503 when gateway is down (readiness — "am I ready to serve?")
  • Auth headers (x-forwarded-access-token) match what our dashboard already sends
  • The host proxy rewrite (/_bff/openshell/api → /api) works correctly

Auth gap (not your problem yet)

The BFF forwards tokens to the gateway. But nobody has proven that the OpenShift oauth-proxy token (what RHOAI users have) works with the OpenShell gateway's OIDC validation. This is the "auth-bridge" story (89726). Not your concern for 89723.

Part 7: What Was Rejected (and Why You Should Care)

Understanding rejected options helps you avoid suggesting them later.

REJECTED: Rewriting the BFF in ODH

What it means: Writing our own Go BFF from scratch in packages/openshell/bff/ that talks to the gateway.

Why rejected: Upstream already has one that works. Reimplementing it doubles the code, and when upstream changes the gateway API, we'd have to update our copy too. Ship their binary, configure it with environment variables.

REJECTED: Sharing React Router / TanStack Query

What it means: Making the host and module use the same copy of these libraries.

Why rejected: Major version mismatch (v6/v7, v4/v5). Sharing would crash. Keep them module-local until upstream bumps to match.

REJECTED: iframe of standalone app

What it means: Loading the entire standalone OpenShell website inside a box on the dashboard page.

Why rejected: No shared auth, no shared styling, double scrollbars, can't control navigation. Demo-only, never production.

DEFERRED: Upstream builds the MF remote

What it means: OpenShell's own build would produce a remoteEntry.js that any host could consume.

Why deferred: Good idea, but only worth it when a second host wants to embed OpenShell. Right now only RHOAI needs it. Keep it simple — we own the adapter.

Quiz

1. What is a "spike" in software engineering?

  • A critical production bug that must be fixed immediately
  • A security vulnerability in the codebase
  • A research task to investigate feasibility and recommend an approach
  • A type of automated test that runs before deployment

2. Why was "ship upstream BFF binary" chosen over "rewrite in ODH"?

  • The upstream BFF is written in a faster language
  • It already works, avoids duplication, and stays in sync with upstream changes
  • ODH doesn't support Go code
  • The team doesn't have Go developers

3. When you switch from mock data to a real BFF, what changes in your React components?

  • You rewrite all fetch calls to point to the BFF URL
  • You change the API prefix in every component
  • You add auth headers to every fetch call
  • Nothing — the proxy config handles routing; components stay the same

4. Why can't React Router be shared between the host and OpenShell module?

  • Major version mismatch (v6 vs v7) — sharing would crash
  • React Router doesn't support Module Federation
  • The host doesn't use React Router
  • Sharing routers creates security vulnerabilities

5. What does "singleton" mean in the Module Federation context?

  • A design pattern where a class can only be instantiated once
  • Only one copy of a library is loaded — the host's version, not the module's
  • A module that has no dependencies
  • A component that renders only once on the page

6. Why was the iframe approach rejected?

  • Iframes are deprecated in modern browsers
  • Iframes don't support React applications
  • No shared auth, styling, or navigation — bad UX for a production product
  • Iframes have a maximum size limit that's too small
