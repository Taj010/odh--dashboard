Lesson 8: One BFF or Two?

Goal: Split the “one BFF or two?” meeting question into three different questions, so you can tell what is already decided and what is still mushy.

Primary source: d0w/openshell-bff-examples — three tiny Go modules that show how downstream (ODH) can reuse upstream (OpenShell) BFF code. Read that repo after this lesson.

Part 1: People are mixing three questions

When someone says “do we need one BFF or two for Agent Ops + OpenShell?”, they might mean any of these:

#QuestionShort answer
1 Two backends? Does listing Sandbox CRs use the same server as administering OpenShell workspaces? No. Two different backends. This is locked.
2 Two processes? Do we run two Go binaries (two ports, two sidecars) in the dashboard pod? Today: yes. A meeting can still change this. Undecided long-term.
3 Two codebases? If ODH needs extra OpenShell behavior, do we fork the BFF or import it as a library? The examples repo says: import and decorate, don’t fork.
The mix-up: Question 3 (how to share Go code) is not the same as question 2 (how many processes run). You can reuse OpenShell’s library and still run two binaries. You can also merge into one binary later. Code reuse does not force one process.
Restaurant analogy: Agent Ops is the kitchen window that talks to the walk-in fridge (Kubernetes Sandbox CRs). OpenShell admin is the office that talks to the security desk (the gateway). Those are two jobs. Whether you hire two people or one person who does both jobs is a staffing choice. Whether the office reuses the security desk’s handbook instead of rewriting it is a third choice.

Part 2: Two backends (this part is locked)

Lesson 1 taught: browser → BFF → Kubernetes. That is only the CR path (Tracks 1 and 2 — list/deploy agents).

Track 3 (your OpenShell admin UI) is a gateway path. Different API, different auth, different owner.

CR path (already shipping)

packages/agent-ops/bff/

  • Port 8843
  • Talks to Kubernetes Sandbox CRs
  • Does SAR/RBAC with the user’s OpenShift token
  • OpenAPI: agent-ops.yaml
  • UI: Agent Deployments list / deploy wizard

Gateway path (Track 3)

Upstream OpenShell BFF (not rewritten in ODH)

  • Port 8943
  • Talks to OpenShell gateway over gRPC
  • Relay-only: forwards a token, gateway enforces RBAC
  • API owned by Epic 2 (Derek / upstream)
  • UI: workspaces, policies, credentials
CR path (Tracks 1–2) Browser → host proxy /agent-ops/api → agent-ops BFF :8843 → K8s Sandbox CRs Gateway path (Track 3) Browser → host proxy /_bff/openshell/api → OpenShell BFF :8943 → Gateway (gRPC)

The frontend already treats them as two APIs. See Lesson 6 (proxy) and Lesson 7 (spike: do not rewrite the OpenShell BFF).

Locked: Spike 81067 rejected “write our own OpenShell BFF inside ODH.” Upstream already has one that speaks gRPC to the gateway. Reimplementing it doubles the work every time the gateway API moves.

Part 3: Two processes (current plan, not a law of physics)

Right now the dashboard would run two Go servers next to the host:

  • agent-ops BFF on 8843 — CR path
  • OpenShell BFF on 8943 — gateway path

That is what “two BFFs” meant in the meeting. Two binaries, two ports, two proxy rules, two deploy/health stories, two things the operator must keep alive.

That does complicate the pod. It is also the simple way to keep ownership clean: Agent Ops team owns CR APIs; OpenShell upstream owns gateway APIs; ODH just ships their binary (story 89726) as a sidecar.

Undecided: merge into one process later?

Someone can propose: “agent-ops BFF imports OpenShell as a Go module and serves both route trees in one binary.” That uses the examples-repo pattern (Part 4). It is a possible later structure. It is not what 89723 needs, and it is not locked.

If they merge processes, your React still calls two URL prefixes. The host proxy still rewrites two paths. Only Kubernetes wiring (one container vs two) changes.

Why two processes feels messy: two health checks, two log streams, two sets of env vars, two auth stories (SAR vs relay), two version pins. Why keeping them separate feels safer: a crash in OpenShell BFF should not take down Agent Deployments, and upstream can release a BFF version without an agent-ops Go bump.

Part 4: The examples repo is about code reuse, not “kill agent-ops”

The spike notes you pasted (“OpenShell Migration Strategies”) and openshell-bff-examples answer question 3:

If ODH is downstream of OpenShell’s Go BFF, how do we customize it without forking?

Upstream publishes packages. Downstream is a tiny main.go that wires them. Go embedding is how you override one method and keep the rest.

The three folders

FolderWhat it proves
upstream/ A real BFF shaped for reuse: Chi router, service interfaces, handlers that only see interfaces, server.NewServer(cfg, svcs, opts...) so extra routes can be bolted on.
downstream-reuse/ ODH runs upstream 100% unchanged. Same handlers, same services. This matches “ship their binary / import their module, add nothing.”
downstream-partialreuse/ ODH still uses NewServer + upstream handlers, but decorates sandbox create, and adds routes upstream never heard of (/api/audit, /debug/ping).

The one trick: embed, override one method

Handlers talk to a SandboxService interface, not a concrete struct. Downstream embeds that interface and redefines only CreateSandbox. Get/List/Delete fall through. Upstream’s HTTP handler does not change — it still calls CreateSandbox, and Go dispatches to the decorator.

type Service struct {
    upstreamservices.SandboxService // inherit Get, List, Delete
}

func (s *Service) CreateSandbox(ctx context.Context, name string) (*Sandbox, error) {
    sb, err := s.SandboxService.CreateSandbox(ctx, name) // real work stays upstream
    sb.Name = name + " (downstream-managed)"             // ODH-only policy
    sb.Status = "provisioning"
    return sb, err
}

That is the decorator pattern with almost no forwarding boilerplate — Go promotes the embedded methods for you (Effective Go — Embedding).

New routes vs changed behavior

From the partial-reuse README, pick the smallest tool:

You need…Do this
Zero changes downstream-reuse: import and run
Same method, different behavior Embed + override that one method
A new method next to the old ones Embed + extend; new interface; new handler
A route OpenShell does not have server.WithRoutes(...) (e.g. audit stats)
Different auth than upstream Raw Chi Option with your own middleware

Part 5: What this means for your work

Ticket 89723 is frontend: wrapper, proxy, mock BFF. You do not choose 1 vs 2 processes.

  • Your UI already has two fetch prefixes if both features exist: /agent-ops/api and /_bff/openshell/api (see Lesson 7).
  • Mocks still sit in front of those prefixes. Process count behind the proxy can change later.
  • Do not put OpenShell workspace calls into the agent-ops BFF “just to have one BFF.” That is the rewrite the spike rejected, unless a later ADR explicitly merges processes by importing upstream.
Ask in the next architecture meeting: “Are we debating two processes, or how ODH customizes the OpenShell module?” If they say “complicates structure,” they usually mean two sidecars (question 2), not two backends (question 1).

Practice: pick the pattern

Click the matching answer. Wrong clicks show the right row.

A. ODH wants OpenShell workspaces with no extra Go behavior.

  • Fork upstream then edit CreateSandbox in their tree
  • Reuse upstream as-is via a binary or module
  • Merge it into agent-ops handlers for those CRs
  • Call the OpenShell gateway from the React app

B. ODH must tag every created sandbox with a RHOAI-only name suffix.

  • Add Chi route that never calls CreateSandbox
  • Rewrite SandboxHandler and copy all four methods
  • Embed the service and override CreateSandbox only
  • Put that suffix into React before submit

C. ODH needs GET /api/audit/sandboxes, which upstream does not have.

  • Attach that new handler via the server.WithRoutes helper
  • Override CreateSandbox and just hope that audit appears
  • List those Sandbox CRs via agent-ops port 8843
  • Ask the host proxy to invent audit JSON

D. Product wants the Agent Deployments table (running Sandbox CRs).

  • Decorate OpenShell CreateSandbox in the downstream Go code
  • Ship only OpenShell BFF and drop agent-ops BFF
  • Point the OpenShell proxy at agent-ops port 8843
  • Just use the existing agent-ops BFF CR path

Quiz

1. The CR path and the OpenShell path talk to:

  • CR path hits Kubernetes; OpenShell path hits gateway
  • CR path hits gateway; OpenShell path hits Kubernetes
  • CR path hits browser; OpenShell path hits cluster
  • CR path hits Cypress; OpenShell path hits webpack

2. What did spike 81067 reject for the OpenShell BFF?

  • Ship the upstream binary as a configured sidecar
  • Rewrite the OpenShell BFF from scratch entirely
  • Mock the OpenShell JSON during the frontend work
  • Proxy the OpenShell API through the dashboard host

3. Embedding a service in the examples lets downstream:

  • Override one method and inherit the rest unchanged
  • Rewrite one handler and delete the rest unchanged
  • Publish one binary and ignore the rest unchanged
  • Fork one module and rename the rest unchanged

4. A new /api/audit route OpenShell does not have should:

  • Embed then override CreateSandbox on that service
  • Attach a new handler via the server.WithRoutes
  • Copy upstream main.go and hope nobody notices
  • Ask the frontend to call Kubernetes by itself

5. For ticket 89723, one vs two BFF processes:

  • Blocks you until they merge both BFF binaries
  • Changes none of wrapper, proxy, or mock work
  • Forces you to write Go for Sandbox CRs
  • Forces you to rewrite OpenShell pages in TypeScript

6. “Two BFFs complicate structure” in a meeting usually means:

  • Two running processes, two ports, two deploy stories
  • Two React versions, two ports, two deploy stories
  • Two CSS themes, two ports, two deploy stories
  • Two Jira boards, two ports, two deploy stories
