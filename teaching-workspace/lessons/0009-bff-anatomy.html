Lesson 9: What a BFF Is Made Of

Goal: Name the parts every ODH BFF has, then mark which parts the CR path and OpenShell can share as a pattern — and which parts must stay unique.

Primary sources: real CR BFF in packages/agent-ops/bff/ (see cmd/main.go, internal/api/app.go), the shared recipe in .claude/rules/bff-go.md, and openshell-bff-examples for the OpenShell-shaped server.

The sandwich

Think of a BFF as a sandwich.

  • Bread = the shell: port, health check, logs, CORS, “read the token header.” Every kitchen uses bread. Same shape, different labels (port numbers, URL prefixes).
  • Filling = the domain: which backend you call, which JSON you return, which permission check you run. CR filling is Kubernetes. OpenShell filling is the gateway.

Your instinct (“ports, API connect, rules — can we group those?”) is right for the bread. It is wrong for the filling. Sharing filling is how you accidentally make the OpenShell BFF do SAR against Sandbox CRs, or make agent-ops speak gRPC.

Three kinds of “share”:
1. Copy the pattern — same fields, different values (every module’s package.json proxy block).
2. Reuse the library — import OpenShell’s Go module (Lesson 8 embedding).
3. Do not merge — one OpenAPI, one K8s client, one SAR middleware for both products.

The stack (outside → inside)

Green = already a shared ODH pattern. Blue = same idea, different numbers. Red = must stay unique to CR or OpenShell.

  • Host · pattern
    Dashboard proxy — package.json module-federation.proxy: path, pathRewrite, authorize: true. Agent-ops uses /agent-ops/api → /api. OpenShell uses /_bff/openshell/api → /api. Same machine; two stamps.
  • Host · pattern
    Ports — every BFF owns one prod port and one local UI port. Agent-ops prod is 8843. OpenShell needs a different number (spike used 8943 as a stand-in). Never share a port. npm run validate:ports exists so two modules cannot pick the same one.
  • Process · shared idea
    HTTP server — listen on PORT, timeouts, optional TLS, graceful shutdown. agent-ops does this in cmd/main.go. The examples repo does it in server.NewServer. Same job.
  • Process · shared idea
    Health — GET /healthcheck so Kubernetes and contract tests know the process is alive. OpenShell’s spike also had /healthz and /readyz (ready = gateway up). Liveness can look the same; readiness is domain-specific.
  • Process · shared idea
    Config flags — PORT, LOG_LEVEL, ALLOWED_ORIGINS, AUTH_METHOD, AUTH_TOKEN_HEADER, mock switches. Same kinds of knobs. OpenShell adds gateway URL / SDK settings; CR adds MOCK_AGENT_CLIENT.
  • Auth shell · careful
    Read the token header — host sets x-forwarded-access-token because authorize: true. Both BFFs read that header. What they do next diverges (next layer).
  • Auth filling · unique
    Rules — CR path: SubjectAccessReview / impersonation against sandboxes in Kubernetes. OpenShell path: relay the token; the gateway checks workspace RBAC (and wants OIDC, not a raw OpenShift opaque token). Do not reuse agent-ops SAR middleware on OpenShell routes.
  • API connect · unique
    Integrations — CR: Kubernetes client, list/get/patch Sandbox CRs. OpenShell: Go SDK, gRPC to the gateway. This is the “API connect” you asked about. It is the filling. Two clients, not one generic “talk to cluster” helper.
  • Contract · unique
    OpenAPI + handlers + models — CR contract is agent-ops.yaml (/api/v1/agents/runtimes…). OpenShell contract is Epic 2’s spec (workspaces, policies…). Two YAML files. Frontends fetch two prefixes. Do not glue them into one spec “to simplify.”
  • Ship · pattern
    Container + Service — Deployment containerPort, Service port, probe on health. Same YAML shape as other modules (89723 checklist / story 89740). Different image, different port.
HOST (already generalized) package.json → proxy + authorize + unique ports │ ▼ BREAD (copy the recipe) listen, logs, CORS, /healthcheck, read token header │ ▼ FILLING (do not merge) CR: K8s + SAR + agent-ops.yaml OS: gRPC SDK + gateway RBAC + OpenShell spec

What you should not generalize

Tempting mergeWhy it breaks
One OpenAPI for CR + workspaces Two products, two owners, two release clocks. Frontend already uses two prefixes.
One Kubernetes client for OpenShell admin Admin data lives on the gateway, not in Sandbox CRs. CR list is a different UI.
SAR middleware on OpenShell routes Wrong permission system. Gateway RBAC ≠ K8s sandboxes verbs.
Same port “because both are agent” Two processes cannot bind one port. validate:ports will fail, or one BFF never starts.
Rewrite OpenShell handlers inside agent-ops Spike 81067 rejected this. Use import/decorate (Lesson 8) if you need extra Go behavior.
If they later run one process: you still keep two fillings. One binary can mount two route trees (Chi Option / two httprouter groups). That is packaging, not “one API.” See Lesson 8.

Optional extra: BFFs calling each other

ODH already has an inter-BFF HTTP client (internal/integrations/bffclient, documented in docs/inter-bff-communication.md). That is how two processes share data without merging fillings — Gen-AI calls MaaS, etc.

CR and OpenShell do not need that for 89723. Only consider it if a screen must combine “running Sandbox CRs” and “gateway workspaces” in one request. Until then: two prefixes from the browser is enough.

What this means for you

On 89723 you configure host bread: proxy, ports, mocks. You do not merge Go fillings. Backend stories (89726 / Epic 2) own OpenShell bread+filling. Agent-ops already owns CR filling.

Unclear which layer a meeting is talking about? Ask: “Are we sharing the proxy/port pattern, importing the OpenShell module, or merging Kubernetes into the gateway BFF?”

Ask the teacher (this agent) if a layer still feels like one blob.

Practice: share or keep unique?

A. Unique production port numbers for each BFF.

  • Merge them so both listen on port 8843
  • Copy the pattern; pick two different port numbers
  • Delete ports; the host proxy invents them
  • Reuse SAR checks instead of using those ports

B. Reading x-forwarded-access-token from the request.

  • Same header idea; both BFFs can read it
  • Only agent-ops may ever read that header
  • Only OpenShell may ever read that header
  • The browser must skip that header always

C. Kubernetes SubjectAccessReview on Sandbox CRs.

  • Share it as OpenShell's only auth check
  • Share it as host proxy only auth check
  • Keep it on the CR path only
  • Run that SAR only inside React components

D. OpenAPI YAML for runtimes vs workspaces.

  • Merge both products into one YAML file
  • Delete YAML; let handlers invent JSON shapes
  • Store both specs only inside the gateway
  • Keep two contracts; two prefixes; two owners

Quiz

1. The “bread” of a BFF is mainly:

  • Port, health, logs, CORS, token header
  • Sandbox CRs, gRPC, SAR, workspace RBAC
  • PatternFly tables, routes, and feature flags
  • Jira epics, stories, blockers, plus tracks

2. “API connect” for CR vs OpenShell should be:

  • One Kubernetes client shared by both fillings
  • One gRPC client shared by both fillings
  • Two clients: K8s for CR, SDK for gateway
  • No clients; the browser calls both backends

3. Host package.json proxy blocks are:

  • Filling you merge into one OpenAPI spec
  • A repeated pattern with different path values
  • Allowed only inside that agent-ops package.json file
  • Replaced by SAR checks inside the gateway

4. Why not put OpenShell routes on port 8843?

  • Kubernetes forbids any listen port except 8080
  • OpenAPI files cannot mention any numeric ports
  • React cannot fetch two different URL prefixes
  • Two processes cannot share one listen port

5. Ticket 89723 mostly configures which layer?

  • Host bread: proxy, ports, and mock replies
  • CR filling: Sandbox create and SAR checks
  • Gateway filling: gRPC SDK and workspace RBAC
  • Operator only: DSC gates with no proxy
